## 1. Executive verdict

**Verdict: REQUEST NARROW CORRECTIONS.** The P2 architecture is sound and I found
no defect in any production trend calculation. Every analytical consumer now
takes one immutable `TrendsPolicy`; `_TRENDS_CONFIG` is read only inside
`app/engine/anomaly/trends.py` and only by the legacy adapter; the pipeline has
no trend/rates read and no global write; the five gates and the authoritative Z
are resolved once per operation; batch reuse, concurrency and stored precedence
are demonstrated by passing tests; the Explain 20% default is consistent with
the engine and the seed; P3/P4 are untouched.

The corrections are about **evidence quality and one compatibility edge**, not
about the architecture:

| ID | Severity | Finding |
|---|---|---|
| A-01 | Moderate | The consumer-scope guard was weakened from exact-set equality to a superset check, so an eighth unapproved consumer would no longer fail. |
| A-02 | Moderate | The architecture guard claims to cover "the trend global" but only detects name-form `set_trends_config` calls and two literal DB-read strings; it does not detect `_TRENDS_CONFIG` reads or attribute-form calls. The source is clean, but the requirement is not enforced. |
| A-03 | Moderate (legacy only) | Malformed raw gate values now fall back silently to defaults; pre-P2 they raised `TypeError`/`ValueError`. The adapter docstring claims unchanged results. Production storage cannot hold such values (`AppConfig.value` is `Float`), so this affects legacy in-process `config=` callers. |
| A-04 | Low | No row-for-row legacy `config=` vs `policy=` equivalence test exists in the suite (only field parity). My audit probe shows equality for a valid config, but requirement 8 is not permanently guarded. |
| A-05 | Low | `explain_anomaly` for trend-anomaly rows still displays the Z threshold from a live `load_analysis_config` read, while `explain_trend_row` now uses the snapshot. Display-only, no stored finding changes, but two Explain paths have different provenance. |
| A-06 | Low | `test_migration_is_limited_to_the_two_run_entry_points` is now misnamed and only guards `confidence`; other unapproved modules are unguarded. Its `RESOLVER_VERSION` change is pre-existing A3.1 work, not P2. |

None of these requires re-architecting P2. All are narrow test/doc corrections.

## 3. Policy immutability and snapshot propagation evidence

* `TrendsPolicy` is `@dataclass(frozen=True)` (`trends.py:53-54`); `__post_init__`
  wraps `bands` in `MappingProxyType` (:72-73). The frozen/mapping behaviour is
  asserted by `test_trends_policy_is_frozen` (`tests/test_a3_5_trends_snapshot.py`).
* Fields (:66-74): `settings`, `bands`, `finding_slope`, `finding_deviation`,
  `finding_cv`, `finding_r_squared`, `trend_r_squared`, `zscore_threshold`.
* `TREND_GATE_KEYS` (:44-50) lists exactly the five raw gates
  (`trend_finding_slope`, `trend_finding_deviation`, `trend_finding_cv`,
  `trend_finding_r_squared`, `trend_r_squared`).
* Adapter `policy_view.trends_policy_from_snapshot` (:69-91) reads
  `analysis_config_from_snapshot` for settings/bands/Z (:79-82, :90) and each
  gate from its own snapshot entry (:83-88). It reads no DB and restates no
  default; `_entry` (:27-34) raises on a missing entry.
* Resolver: `_resolve_trend_engine_gates` (`config_resolver.py:797-833`) derives
  its key set from `TREND_ENGINE_DEFAULTS`, excludes Z/settings/band keys, and
  records each value as `database`/`invalid`/`default`. `_trend_raw`
  (`:430-446`) merges AppConfig then SystemSetting exactly like
  `load_analysis_config`.
* Propagation: the analysis API resolves once (:127) and passes the same object
  to both engines (:135, :178); file_ops resolves once per batch (:688); Explain
  resolves once (:1765) and derives both the engine policy and the displayed
  values from it.
* The setter (`trends.py:129-144`) increments a counter, logs, and writes
  nothing. `_TRENDS_CONFIG` is never mutated by production code.

Stored precedence is demonstrated by
`test_all_five_gates_and_the_window_are_read_from_the_snapshot` (stored values
8.5/33/44/0.9/0.6 and window 6 win) and
`test_explain_uses_a_stored_gate_over_the_default` (stored 33.0 displayed).

## 6. Malformed configuration compatibility assessment

**This is a real behaviour change, and the implementation report understates it
slightly.** Verified by source comparison and a direct probe:

| Input | Pre-P2 (`HEAD` trends.py) | P2 adapter (`trends.py`) |
|---|---|---|
| `config={"trend_finding_cv": "oops"}` | `cv > raw["trend_finding_cv"]` raises `TypeError` (`/tmp/trends_head.py:293`) | `_gate()` catches `TypeError/ValueError` and returns the engine default (`trends.py:104-111`); probe: `cv=30.0` |
| `config={"zscore_threshold": "oops"}` | `float(...)` raises `ValueError` (`/tmp/trends_head.py:388-389`) | defaults to `2.5`; probe: `z=2.5` |
| Malformed trend setting (`window`, enum, …) | `resolve_trend_settings` already coerced to default and recorded `invalid` (`severity.py:433-448`) | unchanged (snapshot records `invalid`) |
| Missing gate | default from `_TRENDS_CONFIG` | default from `TREND_ENGINE_DEFAULTS` — same values |
| Missing policy and missing config | defaults (possibly mutated global) | defaults (setter inert) |

Probe output (run in this audit):

```
cv= 30.0 z= 2.5 defaults= 30.0 2.5
malformed_exit=0
```

Impact assessment:

* **Production stored configuration cannot trigger this.** `AppConfig.value` is
  `Column(Float, nullable=False)` (`app/models.py:662`), and the five gates are
  AppConfig keys (not `NEW_TREND_KEYS`, `severity.py:319-320`), so a stored
  string is impossible through the API/DB. The reachable surface is legacy
  in-process `config=` callers, tests and out-of-tree scripts.
* The adapter docstring says it "preserv[es] old semantics" and that such a
  caller "observes unchanged results" (`trends.py:89-96`). That is true for
  valid and missing values, **not** for malformed gate values. This is a
  documentation/contract defect, not a production calculation defect.
* The implementation report §13 did record the coercion as a robustness change,
  but did not call out that the old path *raised* rather than defaulted, and the
  adapter docstring still claims equivalence.

**Verdict: PASS for stored configuration; FINDING A-03 for legacy malformed
input.** A narrow correction should either document "invalid → engine default"
and add a test, or re-raise for the legacy path if strictness is the contract.

## 9. Remaining limitations

1. **No browser or live-server verification** (constraint: server not started).
2. **No true HTTP-level concurrency test**; concurrency evidence is
   engine/batch-level with a barrier, not two concurrent requests/sessions.
3. **Malformed stored configuration is not exercised end to end**; it cannot be
   stored through `AppConfig` (Float), but the behavior of a malformed legacy
   `config=` payload is only covered by the new unit test for one gate
   (`test_invalid_gate_falls_back_and_is_reported`) and my probe.
4. **Legacy equivalence is probe-verified, not suite-verified** (A-04).
5. **Out-of-tree callers of `set_trends_config` are unobservable.** The shim
   keeps them non-fatal; code that relied on setter-then-call-without-config now
   gets defaults instead of the last-written global. That is the intended P2
   behavior, but it is a compatibility break for such callers and should be in
   the release note.
6. **`analysis.py` catches only `PolicyUnavailable`.** A `KeyError` from a
   snapshot missing a gate would surface as 500; the resolver currently
   resolves all five, so this is not reachable in the tested configuration.
7. **A-01/A-02/A-06 guard gaps** mean future regressions could slip through even
   though today's source is correct.
8. **Explain anomaly rows** still display the live thresholds Z value (A-05);
   no analytical decision uses it.
9. The P0 golden fixture remains a forward-looking lock, not a pre-P2 baseline.

## 10. Recommendation

**Request narrow corrections; do not reject P2 and do not start P3 until they
are addressed.** The corrections are test/doc changes and do not touch the trend
formulas or the resolved values:

1. **A-01** — restore an exact assertion for the policy-view consumer set (or
   an explicit equality against an allowlist), and rename
   `test_only_the_two_run_entry_points_consume_the_snapshot` to reflect the
   A3.5 scope.
2. **A-02** — extend the AST guard to flag loads of `_TRENDS_CONFIG` outside
   `trends.py` and attribute-form `*.set_trends_config(...)` calls; then the
   test name matches what it proves.
3. **A-03** — decide and encode the malformed-legacy-gate contract: either
   document the fallback in the adapter docstring (and keep the test), or
   restore raising for `config=` callers. Update the "unchanged results" claim.
4. **A-04** — add a row-for-row `config=` vs `policy=` equivalence test for both
   `analyze_historical_trends` and `detect_trend_anomalies` (the probe already
   shows equality; the suite should own it).
5. **A-05/A-06** — either migrate `explain_anomaly`'s trend-row Z display to the
   snapshot or label it as a display-only legacy read; tighten and rename
   `test_migration_is_limited_to_the_two_run_entry_points` to an explicit
   allowlist (its `RESOLVER_VERSION` 1.3.0 line is pre-existing A3.1 work, not
   P2).

After those, P2 should be acceptable for P3 planning. The Z=2.5, bands,
cutoffs, peer policies, caps and all stored findings remain unchanged and are
verified by the passing suites above.
