# A3.5 — P3.1 Confidence Snapshot Integration: Read-Only Audit and Design

Date: 2026-11-03. Scope: investigation and design for moving Confidence
weights and thresholds onto an immutable, snapshot-derived `ConfidencePolicy`.
**No production code or test was modified. No migration, backfill, recalculation,
server start, or production database access occurred.**

---

## 1. Executive summary and verdict

Confidence is the last analytical plane that still reads its own policy from the
database and writes process-global state. One function,
`calculate_confidence`, does all of it:

* reads `confidence_weights.first()` and `thresholds` through a second
  `get_config_dict` call;
* **rebinds the module-level `SIGNAL_WEIGHTS` dict on every call with a session**
  (`confidence.py:427-437`);
* swallows every exception from both reads (`except Exception: pass`);
* computes each indicator from whatever the global contains at that instant
  (`:479`).

The API's `GET /confidence/weights` **inserts and commits a row when none
exists** (`api/confidence.py:207-221`), and the Settings page calls that GET on
load. The table has no uniqueness constraint, so two concurrent first reads can
create two rows; `.first()` is then arbitrary. The PUT accepts partial and
negative payloads as long as the *provided* subset sums to 1.0, so the stored
row's real total can be 1.45 or 1.35 (proved on temporary SQLite below).

The resolver already resolves the three confidence cutoffs and the Z threshold
as `confidence.*` entries, but it does **not** resolve the five weights, and
nothing consumes the confidence plane yet. Adding the weights to the snapshot
will change every snapshot digest unless it is deliberately excluded; excluding
an analytical input would make the digest lie, so the correct design is an
explicit resolver-version bump and a new digest baseline approved in P3.2.

**Verdict: READY FOR P3.2 DESIGN APPROVAL**, conditional on four explicit
decisions (read-only GET, duplicate-row policy, digest/version change, malformed
weights policy). No blocking semantic ambiguity was found. Production table
contents and duplicate prevalence were **NOT VERIFIED** — no production
connection was made.

## 3. `confidence_weights` schema and read/write inventory

### Schema

`app/models.py:645-656`:

```python
class ConfidenceWeights(Base):
    __tablename__ = "confidence_weights"
    id = Column(Integer, primary_key=True, index=True)
    rule_compliance = Column(Float, nullable=False, default=0.55)
    historical = Column(Float, nullable=False, default=0.10)
    cross_hospital = Column(Float, nullable=False, default=0.10)
    trend = Column(Float, nullable=False, default=0.10)

The initial migration (`f25afbb94bc7_initial_schema.py:49-61`) creates exactly
those columns, a primary key on `id`, and a **non-unique** index
`ix_confidence_weights_id`. There is no singleton key, no unique constraint on
any weight column, and no check constraint. The temporary SQLite probe confirmed
the only index is `('ix_confidence_weights_id', ['id'], unique=0)`.

### Writers

| Path | What it writes | Commit |
|---|---|---|
| `GET /confidence/weights` (`api/confidence.py:207-221`) | If `.first()` is `None`: constructs a row with hard-coded defaults and adds it | `db.add`; `db.commit`; `db.refresh` |
| `PUT /confidence/weights` (`api/confidence.py:225-249`) | `.first()`, or a new `ConfidenceWeights()`; sets only supplied fields; checks the supplied subset sums to 1.0; commits | `db.commit`; `db.refresh` |

| `scripts/migrate_sqlite_to_pg.py:47` | Copies the table between stores; not an application writer | migration script |

No dashboard, analysis, preview, export, tree, upload, alert, or report path
creates or updates `confidence_weights`. The only application writes are the two
`/confidence/weights` endpoints, and the GET is reached by the Settings page's
`loadWeights()` (`static/js/rules-manager.js:230-235`, invoked at `:3191`).

### Readers

* `calculate_confidence` (`confidence.py:429-437`): `session.query(ConfidenceWeights).first()`.
* `GET /confidence/weights` (`api/confidence.py:209`): `.first()`.
* `PUT /confidence/weights` (`api/confidence.py:228`): `.first()`.

No other application module imports `ConfidenceWeights`.

### The eight questions

1. **Exactly one intended record?** Yes *by intent* — every consumer uses
   `.first()` and the UI presents one set. It is **not enforced**: no unique
   constraint, no singleton key, no startup seed.
2. **Zero records?** `calculate_confidence` leaves `SIGNAL_WEIGHTS` at whatever
   it already contains (normally the module defaults); GET inserts defaults;
   PUT inserts a row from column defaults. Thus zero rows is a normal state and
   does not, by itself, produce defaults on a warmed process.
3. **Multiple records?** `.first()` without `order_by` returns an
   implementation-dependent row. The probe inserted two rows and got id 1 on
   SQLite; PostgreSQL may return a different one. GET/PUT/calculation can each
   see a different row, and PUT updates only that one.
4. **Two simultaneous first reads?** Both can observe zero rows, both add, both
   commit; duplicates are possible. There is no unique constraint to lose the
   race safely. GET and PUT both have this race.
5. **Does GET create a row?** **Yes.** It is a mutating read: a user with only
   `analysis.read` (the router-level dependency) causes a settings write merely
   by opening the Settings page.
6. **Any other path creating/modifying?** No. Analysis reads only; dashboard,
   preview, exports and alerts only read stored `ConfidenceScore` rows, not
   `confidence_weights`.
7. **Stored vs defaults?** The five weights are stored in this table. The
   cutoffs (`confidence_high/medium/low`) and `zscore_threshold` are stored as
   AppConfig `thresholds` rows. Defaults exist in four places for weights
   (module table, model column defaults, GET literals, PUT's `ConfidenceWeights()`
   column defaults) and in three places for cutoffs (`APP_CONFIG_DEFAULTS`,
   `_compute_level` literals, resolver `_CONFIDENCE_DEFAULTS`).
8. **Validated/normalized?** No normalization anywhere. PUT checks only that the
   **provided** values sum to 1.0 ±0.01; it does not require all five fields,
   does not check range or finiteness, and does not verify the resulting row's
   total. The engine trusts whatever is stored. The only clamp is the final
   confidence score to `[0, 100]` (`confidence.py:480`).

Temporary-SQLite evidence (deliberate fixture, not production):

```

stored_row_global {'rule_compliance': 0.2, ..., 'completeness': 0.2} score 82.0

The 82.0 after deleting rows proves the global persists the previous request's
weights when the row disappears.

## 4. GET endpoint side-effect analysis

`GET /confidence/weights` is registered under the router prefix `/confidence`
with router-level `require_permission("analysis.read")`
(`api/confidence.py:24, 207`). Its complete call chain is:

```
GET /confidence/weights
  -> require_permission("analysis.read")
  -> get_db()                       (new Session, closed in finally; no rollback)
  -> db.query(ConfidenceWeights).first()
  -> if None: ConfidenceWeights(defaults literals); db.add; db.commit; db.refresh
  -> return five fields
```

There is no service layer, cache, or read-only flag. The Settings page calls
this GET at load, so **opening Settings is a write** for any user with analysis
read permission. A read-only replica or a connection in a read-only transaction
would fail the request. The response shape is five numbers; the side effect is
not advertised.

Two concurrent first GETs can each see no row and insert; the second commit does
not fail because nothing is unique. A concurrent PUT has the same
insert-if-missing race. Once duplicates exist, GET/PUT/calculation each use
`.first()` with no ordering, so the effective weights can change between
requests without any user action.

This is independent of the confidence calculation's own global-state defect,
but it makes the storage non-deterministic in exactly the situation where a
first analysis is likely to run.

## 5. `SIGNAL_WEIGHTS` global mutation and concurrency findings

All application references:

| Location | Operation |
|---|---|
| `confidence.py:41-47` | module-level dict, defaults |
| `confidence.py:427` | `global SIGNAL_WEIGHTS` |
| `confidence.py:434-440` | **rebinds** it to a new dict from `ConfidenceWeights.first()` |
| `confidence.py:479` | reads it for every indicator: `sum(s.score * SIGNAL_WEIGHTS.get(...))` |

No other app module reads, replaces, or mutates it. Tests do not reference it
directly. Documentation examples do, but are not executed.

### Confirmed defects

1. **Per-call global write.** A request with a session rebinds process-wide
   state. The write is not restored in a `finally`, so the last request wins for
   every later caller that has no session (all direct engine tests and any
   future caller omitting `session`).
2. **Missing row uses previous request's values.** The probe proved this:
   after a 0.2-each row was used, deleting the row and calling without one
   produced 82.0, not the 91.0 default.
3. **Concurrent contamination.** Thread A sets its weights, thread B sets
   different weights, thread A reads `SIGNAL_WEIGHTS` again for its next
   indicator. The reassignment and reads are separate bytecode operations; the
   GIL does not make the sequence atomic. Two runs can therefore mix weight sets
   within one result.
4. **Silent read failure.** Weights and thresholds are in one `try` with
   `except Exception: pass`. A transient weights-query failure also suppresses
   the threshold read, and the run continues with whatever global/cutoff state
   was left behind.
5. **Double read within one analysis.** `pipeline._compute_full_analysis`
   already holds a `PolicySnapshot`, and the Confidence API already holds a
   display snapshot, yet `calculate_confidence` opens a second configuration read
   for weights and thresholds. A configuration change between the snapshot and
   this read makes the run disagree with itself.
6. **No provenance.** The stored `ConfidenceScore` row records no weights,
   cutoffs, Z, resolver version or digest.

### Consumer matrix

## 6. Confidence thresholds and defaults

`_compute_level` (`confidence.py:347-358`) reads:

| Field | Current storage | Default | Consumer | Behavior |
|---|---|---|---|---|
| `confidence_high` | AppConfig `thresholds` | `80.0` | `_compute_level` for each indicator and overall | `>= high` → HIGH |
| `confidence_medium` | AppConfig `thresholds` | `50.0` | same | `>= medium` → MEDIUM |
| `confidence_low` | AppConfig `thresholds` | `25.0` | same | `>= low` → LOW; below → CRITICAL |
| `zscore_threshold` | AppConfig `thresholds` | `2.5` | `_signal_historical`, `_signal_cross_hospital` pass/fail display | **raw**, not clamped and not rounded; severity clamps a separate entry |

`APP_CONFIG_DEFAULTS` seeds the four keys at startup (`main.py:96-98` and the
existing `zscore_threshold` row). Missing keys are handled by literals in
`_compute_level` and `get_config_dict` returns `{}`; malformed values are
unreachable through `AppConfig.value` (`Float`, `nullable=False`), but a missing
row or a manually corrupted database would fall back to the literals.

The resolver already produces `confidence.high`, `confidence.medium`,
`confidence.low`, and `confidence.zscore_threshold` (`config_resolver.py:683-723`)
with exactly the raw values above; its confidence plane is **not consumed by
`calculate_confidence`**. Note the deliberate difference from
`severity.zscore_threshold`: severity clamps to `[1,5]` and rounds; confidence
does neither. A `ConfidencePolicy` must use the **confidence** entry, not the
trend/severity one, or behavior changes for stored Z outside the severity range.

No ordering validation exists for the three cutoffs (e.g. low > medium), and no
clamping. That is existing behavior to preserve unless a separate policy change
is approved.

## 7. Proposed immutable `ConfidencePolicy`

Proposed shape (design only — not implemented):

```python
@dataclass(frozen=True)
class ConfidencePolicy:
    # signals
    rule_compliance: float
    historical: float
    cross_hospital: float
    trend: float
    completeness: float
    # levels
    high: float
    medium: float
    low: float
    # signal pass/fail
    zscore_threshold: float
    # provenance
    weights_source: str          # database | default | invalid | unavailable
    thresholds_source: str
    version: str = "1.0.0"
```

| Field | Source | Default | Precedence | Type / validation | Consumers | Identity |
|---|---|---|---|---|---|---|
| `rule_compliance` | one canonical `confidence_weights` row | `0.55` | stored row > code default | `float`; finite required; sum/range decision below | weighted score | analytical |
| `historical` | same | `0.10` | same | same | weighted score | analytical |
| `cross_hospital` | same | `0.10` | same | same | weighted score | analytical |
| `trend` | same | `0.10` | same | same | weighted score | analytical |
| `completeness` | same | `0.15` | same | same | weighted score | analytical |
| `high` | `confidence.high` | `80.0` | stored > default | `float`; no clamp/order normalization | level | analytical |
| `medium` | `confidence.medium` | `50.0` | same | same | level | analytical |
| `low` | `confidence.low` | `25.0` | same | same | level | analytical |
| `zscore_threshold` | `confidence.zscore_threshold` | `2.5` | stored > default | `float`; raw (no severity clamp) | historical/cross-hospital `passed` and recommendations | analytical (output changes even though score does not) |

Semantics preserved exactly:

* weights are used unnormalized: `sum(score * weight)` then `* 100`, clamped to
  `[0, 100]`;
* missing weights use the five code defaults, not zeros;
* missing cutoffs use 80/50/25; missing Z uses 2.5;
* the Z threshold is the raw `thresholds.zscore_threshold`, not the clamped
  severity value;
* no new fields, no changed signal definitions, no changed formulas.

Validation policy to approve in P3.2:

* always reject/record non-finite values (`NaN`, `±inf`) rather than pass them
  into arithmetic and JSON;
* decide whether negative weights or totals outside 1.0 ±0.01 are `invalid`
  (would change results for a malformed stored row) or are carried as-is to
  preserve current arithmetic. Recommendation: enforce range and total **at the
  write boundary**, keep the read policy value-exact for any finite stored row,
  and record a `weights_valid` flag/error; do not silently normalize, because
  normalizing at read would make the digest disagree with what the engine uses.
* duplicates: see §10; the policy loader needs one deterministic decision before
  it can build the object.

Presentation-only? None of the fields is presentation-only; all affect a
computed score, level, signal or recommendation. A UI preview must therefore
read the same effective values, but the preview itself is not part of identity.

## 8. Snapshot and digest implications

### How the table enters the snapshot

`load_policy_snapshot(db)` (`config_resolver.py:1057-1096`) currently reads
`AppConfig`, `SystemSetting`, and `rules_version` once. The natural extension is
one additional query for `ConfidenceWeights` in the same function, passed into
the pure `resolve_policy` as an optional argument (so the pure resolver remains
DB-free and testable). `_resolve_confidence` would add five entries, e.g.
`confidence.weight.rule_compliance`, etc., component `confidence`, storage
`confidence_weights` (a new storage label, since it is neither `app_config` nor
`system_settings`).

A missing row resolves to the five code defaults with source `default`. A
present row resolves to `database`. A table read failure in strict mode raises
`PolicyUnavailable` like the other stores; in display mode it marks the
confidence entries `unavailable` with defaults.

### Digest

**Adding the weights changes every snapshot digest.** `PolicySnapshot.digest`
hashes `canonical_json()`, which includes every `values` entry; five new keys
therefore change the bytes even when their values are the defaults. There is no
way to add an analytical input and keep the old digest without excluding it from
identity, which would be incorrect.

Recommendation: treat this as an intentional, separately approved identity
change:

* bump `RESOLVER_VERSION` from `1.3.0` to `1.4.0` (or the next approved
  version);
* update `component_versions["confidence"]` to the policy version;
* re-baseline digest/golden tests in P3.2 with an explicit note that all digests
  change once, and record one before/after pair;
* never exclude weights via `PROVENANCE_METADATA_KEYS`; they are not
  provenance, they are analytical policy.

If strict digest compatibility is mandatory, the alternative is a separate
`confidence_digest` outside the main identity digest, but that hides a real
analytical input and is **not recommended**.

### Canonical ordering

Use a fixed dataclass field order and the existing `_normalise`/sorted-key JSON.
The five weights are a fixed-name mapping, so insertion order cannot affect the
digest. No sequence/ordering normalization is needed.

### Normalization

Do not normalize at read. The current engine accepts the stored row as-is; a
read-time normalization (e.g. dividing by the total) would change results and
make the digest describe different numbers than the calculation uses. If
normalization is desired, do it at the PUT write boundary before persistence,
then snapshot the canonical stored values. This is a separate behavior change
and must be approved.

### Historical confidence provenance

**No exact provenance exists.** `ConfidenceScore` stores
`overall_confidence`, `level`, counts, `indicators_data` (signal scores/details)
and `created_at`; it has no weights, cutoffs, Z threshold, policy digest,
resolver version or settings snapshot. The signals' factor scores are not the
weighted contributions, so old scores cannot be reconstructed exactly from
`indicators_data` plus today's settings. Do not claim that historical rows can be
associated with the exact settings used.

Future provenance options, both separate from P3.1:

1. add a nullable JSON/text provenance column to `confidence_scores` (migration,
   backfill only for new rows, old rows remain unknown);
2. persist the Confidence policy envelope inside `indicators_data` (no schema
   migration, but changes the JSON contract and all readers; not recommended
   without a versioned envelope).

Until one is approved, reports should describe stored confidence as historical
output with unknown settings provenance, not as reproducible under current
settings.

## 9. Historical provenance limitations

* No confidence row records the weights, cutoffs, Z, resolver version, digest,
  or even whether defaults were used.
* `ConfidenceScore.created_at` is a write time, not a configuration identity.
* Stored `indicators_data` contains signal scores and details, but the applied
  weights are not serialized and the weighted sum cannot be uniquely inverted.
* A settings change followed by no recomputation leaves old scores displayed
  under the new UI/current policy with no marker.
* The table has no unique `(hospital_id, month)` constraint either, so "the"
  stored row for a month is itself `.first()`; this audit did not verify whether
  duplicates exist in production.

P3.2 can make **future** runs reproducible (snapshot digest available at write
time) without a migration only if it records provenance somewhere; without a
column/json-contract change it cannot. P3.1 therefore treats provenance as a
separate, explicitly migration-bearing decision.

## 10. Read-only GET versus row-creation recommendation

### Option A — read-only GET (recommended)

* GET resolves the effective `ConfidencePolicy` from the snapshot/loader and
  returns its five weights (defaults when no row), without `add`, `commit` or
  `refresh`.
* GET never creates or modifies a row; it is safe on a read replica and for a
  read-only permission.
* Writes occur only through PUT (or an explicit seed/admin command).
* No migration is required. A missing row remains a legitimate "defaults" state.
* Behavioral change: the first Settings load no longer creates a row. Any code
  that assumed a row exists after GET must be checked (search found none; PUT
  and calculation already handle `None`).
* Add a test asserting row count stays zero across repeated GETs and that the
  response equals the documented defaults.

### Option B — preserve row creation

* Document the side effect and the required write capability on a read endpoint.
* Two concurrent first reads can create duplicates; `.first()` is arbitrary;
  PUT updates one arbitrary row; calculation may use another.
* A unique constraint requires a migration. Because the table has no natural
  singleton key, it needs a new column/constraint (e.g. a singleton flag with a
  unique index, or a check that `id = 1`), plus a cleanup decision for existing
  duplicates. A unique index on `id` does **not** prevent multiple rows.
* Existing duplicates cannot be deduplicated blindly: they may contain
  different weights and there is no timestamp-based "intended" row guarantee.
  A migration must choose an explicit rule and be separately approved.
* Even with uniqueness, GET still performs a write on a read path and still
  fails on read-only replicas.

**Recommendation: Option A.** It removes the race and the permission inversion
without a migration. Keep PUT as the only writer; if the team wants a guaranteed
row, add an idempotent seed/admin operation, not a GET side effect. Treat the
unique-singleton migration as a separate proposal only if production inspection
finds duplicates or the team requires database enforcement.

## 12. Risks and unresolved decisions

1. **Duplicates already in production.** The code permits them; their existence
   is **NOT VERIFIED** (no production connection). P3.2 must define strict vs
   deterministic behavior before reading `.first()` again.
2. **Digest break.** Adding weights changes every digest. Approve the version
   bump and baseline change, or explicitly choose a separate digest (not
   recommended).
3. **Malformed weights.** Preserve exact arithmetic for finite stored rows, or
   reject negative/total≠1 at read? Recommendation: validate at write, record
   validity, do not normalize at read. This is an approval item because it
   affects behavior for a malformed row.
4. **Read-only GET is a behavior change.** Any external client that relied on
   the row appearing after GET must be updated; repository search found none.
5. **Display vs analysis strictness.** `api/confidence.py` uses
   `load_display_policy` (non-strict, unavailable entries become defaults), while
   the analysis pipeline uses strict `load_policy_snapshot`. P3.2 must state
   which policy the live confidence endpoint uses; a display path should label
   unavailable configuration rather than silently claim defaults.
6. **Provenance needs a schema or JSON-contract change.** Do not promise exact
   historical reproducibility without it.
7. **Unique singleton constraint needs a migration.** Keep it separate from the
   no-migration P3.2 core.
8. **Settings preview** currently falls back to 0.2 per weight when an input is
   missing; after P3.2 it must display the effective policy, not an independent
   hard-coded default.
9. **Global removal compatibility.** `SIGNAL_WEIGHTS` is a documented-ish module
   symbol; P3.2 should keep a deprecated read-only default for import
   compatibility or explicitly update all importers (application search found
   none outside the module). Do not keep it writable.
10. **No production verification.** Table contents, duplicate count, and actual
    stored values are unverified. All findings are from source plus temporary
    SQLite.

No stop condition was triggered: the weights semantics are determinable; the
duplicate rows in the probe were deliberately injected, not unexpected fixture
data; no production data was touched; no migration is necessary for the core
policy work; and no formula change is required.

## 15. Recommendation

**P3.2 design approval is recommended**, with these four decisions made
explicitly in the approval:

1. **GET is read-only (Option A)**; PUT is the only writer; no uniqueness
   migration in the core phase.
2. **Duplicates fail loudly in analysis** (or a documented deterministic
   selection for display); never leave `.first()` arbitrary.
3. **Resolver version/digest changes once** because weights are analytical
   identity; no exclusion from the digest.
4. **Weights validation occurs at the write boundary**, with read-time values
   kept exact for finite stored rows and non-finite values rejected/recorded.

Once those are approved, P3.2 can implement `ConfidencePolicy`, pass it through
the existing snapshot to both `calculate_confidence` call sites, remove the
global write, and make GET side-effect-free without touching any formula,
signal definition, cutoff, band, Z threshold, Rules or Trends behavior. Exact
historical confidence provenance remains **not available** and requires a
separate, migration-bearing decision.
