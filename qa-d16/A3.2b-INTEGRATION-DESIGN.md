## 1. Configuration planes

A plane is a **classification of a setting by the output it can change**, not by its storage
category, its seed list, or its name. Every classification below is backed by a traced consumer;
the trace lives in `A3.2b-COVERAGE-MATRIX.md`.

### P1 — Analysis values

Settings that enter a calculation: severity bands, trend specs, scoring weights, confidence
cutoffs, rule factors, ML hyper-parameters, alerts criteria, comparison windows.

* Already resolved (A3.1): 57 entries across `severity`, `alerts`, `comparison`, `scoring`,
  `confidence`, `trend`, `rules`, `ml`.
* Target additions in P1 (later step, smart only): `smart.contamination`,
  `smart.lof_neighbors`, `smart.dbscan_eps`, `smart.dbscan_min_samples`,
  `smart.threshold_green`, `smart.threshold_yellow`, `smart.ensemble_*_weight` (4),
  `smart.fdr_q`, `smart.pattern_min_support` — 12 values.

### P2 — Analysis gates (execution eligibility)

Boolean or categorical switches that decide *whether* an operation runs or *which rows* qualify.
They are values in the snapshot (`PolicyEntry`), never a separate storage type — a separate type
would change `canonical_json()` and break the A3.1b digest contract for no benefit.

| Setting | Gate semantics today | Effect when off/false | Plane owner |
|---|---|---|---|
| `auto_disable_null_indicators` | read 7 times, 16 dependency sites | NULL-valued and missing indicators leave the completeness denominator; the confidence assessed list stops back-filling them | **analysis** |
| `alerts.auto_scan` (resolved A3.1) | `_maybe_auto_scan_quality_alerts` | no alert scan follows an analysis | **analysis** |
| `ml.enabled` / `ml.clustering_enabled` / `ml.anomaly_enabled` / `ml.pca_enabled` | `pipeline` + `run_ml_analysis` | the ML step is skipped; score unaffected | **analysis** |
| `trend.trend_assessment_enabled` | severity engine | no trend result, no trend escalation | **analysis** |
| `smart.enabled` | `run_smart_analytics` gate | anomalies/clustering/patterns suppressed; **XGBoost still runs** | **smart** |
| `smart.xgboost_enabled` | separate gate | XGBoost path skipped | **smart** |
| `smart.shap_enabled` | `explain_anomalies` | explanations empty | **smart** |

Two gate asymmetries are preserved as-is, not "fixed":

1. `smart.enabled = 0` does **not** stop `run_xgboost_predictions`; only `smart_xgboost_enabled`
   does. A snapshot must expose both flags and no consumer may collapse them.
2. `smart.enabled` is not even passed to `analyze_correlations` or `run_stratified_analysis` —
   they receive `config` but read no `enabled` key. Correlations therefore run with smart analytics
   "off". Any integration that adds an `enabled` check there would change output.

### P3 — Dashboard and presentation gates

Settings that change what a dashboard screen displays or detects, without changing any stored
`QualityScore` or `QualityAlert` row.

| Setting | Consumer | Effect | Stored result affected? |
|---|---|---|---|
| `anomaly_drift_months` | `dashboard/attention` (`_drift_len`) | which hospitals appear as "slow decline", and the reported `months` value | **No** — dashboard recomputes on read |
| `hide_explanatory_text` | report rendering | blanks narrative sections per user | No (presentation of an existing result) |
| `upload_incremental_months`, `structured_logging_enabled`, `slow_query_logging_enabled` | operations | not policy | No |

`anomaly_drift_months` is the only P3 setting proposed for the snapshot in A3.3, because it is the
only one with a detection consumer. The operational flags stay outside every snapshot and every
digest: nothing in the analysis or dashboard result depends on them.

### P4 — Rule identity and provenance

Preserved exactly as A3.1b defined it:

* `RULE_DEFAULTS` stays a `MappingProxyType` captured at import; the resolver reads defaults from
  it, never from the mutable `_RULES_CONFIG`.
* `rules.hash` covers every non-`id`, non-`*_at` column, ordered by UNIQUE `code`, canonical JSON,
  `params` parsed and re-serialised. Primary keys, row order and JSON formatting cannot move it.
* `rules.updated_at` is provenance: present on `PolicySnapshot.metadata`, excluded from
  `canonical_json()` through `PROVENANCE_METADATA_KEYS`.
* New proposal: each entry gets a `scope` tag (`analysis` | `smart` | `dashboard`) and gates are
  additionally tagged `flag`. The tag is **not** serialised into `canonical_json()`; it selects
  which scope digest an entry feeds. This keeps A3.1b's digest bytes unchanged for existing keys.

### Explicit non-placements (evidence-based)

| Setting | Not placed because |
|---|---|
| `rates.*` (7) | read only to merge into a legacy trend dict whose keys are then ignored; no analytical reader |
| `clinical.*` (30), `risk.*` (12) | seed + display only; no engine reader |
| `ai_*` (7) | includes `ai_api_key`; a credential must never enter a snapshot or digest |
| `month_enabled_*` | they gate whether a hospital/month is analysed at upload time, not what the analysis computes. Adjacent finding: this is an eligibility decision outside the snapshot's current scope; it belongs in its own increment. |
| `smart_xgb_n_estimators`, `smart_xgb_max_depth` | **no consumer exists.** `xgboost_predictor.ENSEMBLE_CONFIGS` is a module constant `(80,3) (150,5) (200,7)`; neither key is read anywhere in `app/engine/smart/` |

### 2.2 Bulk analysis: one policy per batch

**Recommendation: one snapshot per batch**, created before the loop in the batch entry and passed
to every item. Justification:

* Every bulk path uses one session for the whole batch (verified in `analysis.py:_run` and
  `recompute_hospital_months`), so a per-item snapshot adds no isolation - it only re-reads.
* The batch writes derived rows; a mid-batch configuration change would otherwise make hospitals
  in the same batch incomparable while both claim the same run.
* Nothing in the analysis path writes configuration, so a batch-long snapshot cannot become stale
  in a way that matters to the batch's own writes.

**Exception (must stay per-item):** `recompute_hospital_months` purges and recomputes month by
month inside one session; it should still take one batch snapshot, because the purge is not a
configuration write. No path in the repository needs per-hospital policy within a batch.

### 2.3 What "one snapshot" does *not* yet mean

`_compute_full_analysis` already receives the snapshot, but still executes:

```python
rules_config = get_config_dict(session, "rules");   set_rules_config(rules_config)
trends_config = get_config_dict(session, "trends")  # merged with rates + snapshot trend gates
ml_config = get_config_dict(session, "ml")
quality_config = get_config_dict(session, "quality")
```

per hospital, and mutates two process-global dicts per hospital. So today the run shares one
configuration **only for the planes the resolver owns**. A3.3 must not claim otherwise, and must not
copy this pattern for the flags plane: the flag is read once at the boundary and passed as a value.

The `alerts_auto_scan` case shows the same gap in miniature: the resolver resolves
`alerts.auto_scan` (A3.1) but `_maybe_auto_scan_quality_alerts` re-reads the AppConfig row, and
`alerts_config_from_snapshot()` does not even return the key.

## 3. `auto_disable_null_indicators` integration design

### 3.1 Current semantics (frozen for this design)

| Property | Value |
|---|---|
| Storage | `SystemSetting(key="auto_disable_null_indicators")`, text |
| Seeded | **No.** Absent until an operator saves it. |
| Producer | exactly **one**: `PUT /config/control/settings` -> `update_control_settings`, `str(value).lower()`, no validation |
| Default when absent | `False` |
| Enabled iff | `row is not None and row.value == "true"` — exact, case-sensitive, no strip |
| `"TRUE"` / `"True"` / `"1"` / `"yes"` / `"true "` | all **OFF** |
| When ON | indicators with a `NULL` value row **and** indicators with **no row at all** are added to the disabled set for that hospital/month |
| Manually disabled | unaffected — always disabled regardless of the flag |
| Completeness denominator | **changes**: null + missing leave the denominator through `get_required_indicator_ids` |
| Completeness numerator | **does not change**: `get_enabled_values_for_hospital_month` subtracts only *manual* disable (correction to the A3.2 report, see the corrected matrix) |
| Confidence | **changes**: the assessed list stops back-filling key indicators absent from `values` |
| Outlier-penalty denominator | **does not change** — `outlier_eligibility` deliberately ignores auto-disable |
| Validation context | `disabled_codes` gains the auto-disabled codes, so rules that reference them see them disabled |

### 3.2 Read sites (complete)

**Direct reads of the setting (7):**

| Site | Behaviour on DB error |
|---|---|
| `pipeline._is_auto_disable_null` (`103`) | raises |
| `pipeline.get_disabled_indicator_ids` (`348`, via helper) | raises |
| `smart/__init__._disabled_maps` (`60`, via helper) | raises |
| `indicator_groups` preview (`440`, via helper) | raises |
| `tree_config` enrichment (`345`) | raises |
| `dashboard` completeness prefetch (`1519`) | **swallows -> False** |
| `confidence.calculate_confidence` (`452`) | **swallows -> False** |
| `config_api.get_control_settings` (`241`) | display only, raises |

**Sites that inherit the decision through `get_disabled_indicator_ids` (9):**
`pipeline.py:289`, `pipeline.py:335`, `pipeline.py:472`, `pipeline.py:644`,
`pipeline.py:1017`, `api/clinical.py:51`, `api/confidence.py:65`,
`api/rules.py:384`, `api/rules.py:556`.

**Two further callers reach it through `get_required_indicator_ids`:**
`pipeline.py:316` (`get_required_indicator_codes`) and `indicator_groups.py:477`.

**Total:** 10 modules, 16 read sites, 18 dependency edges. (A3.2 reported 6 modules / 7 sites;
that counted only direct reads — corrected in `A3.2b-COVERAGE-MATRIX.md`.)

### 3.3 Single-resolution design

```python
# proposed signatures (NOT implemented in this phase)
def get_disabled_indicator_ids(session, hospital_id, month, *,
                               auto_disable_null: bool) -> list[int]: ...
def get_required_indicator_ids(session, hospital_id, month, *,
                               auto_disable_null: bool) -> list[int]: ...
def get_required_indicator_codes(session, hospital_id, month, *,
                                 auto_disable_null: bool) -> set[str]: ...
```

Rules that make this safe:

1. **No `None` default.** A keyword-only required bool means a forgotten call site is a
   `TypeError` at test time, not a silent extra DB read. The A3.2 design note "optional parameter
   defaulting to a DB read" is rejected for this reason.
2. **The value comes from `PolicySnapshot.flags["auto_disable_null_indicators"]`** — a
   `MappingProxyType` view over the same entries, so `snapshot.values` remains the single source.
3. **Boundary shim only.** `_is_auto_disable_null(session)` is reduced to
   `resolve_analysis_flags(session)["auto_disable_null_indicators"]` for the four display/preview
   endpoints that hold no snapshot, and is deleted from `get_disabled_indicator_ids`. Analysis
   paths never call it.
4. **Parsing is not re-implemented.** The resolver reproduces `row.value == "true"` exactly and
   records `source="database"` + `raw` (or `source="default"` when absent). No `str.strip()`, no
   truthiness, no `bool("false")` bug.
5. **Completeness paths stay composed.** `compute_hospital_completeness`,
   `compute_hospital_completeness` callers, `_compute_full_analysis` and the dashboard recalc must
   all pass the same bool; the three completeness call sites are already documented as needing to
   compose through one helper, so this is the same doctrine applied to the flag.
6. **Eligibility is computed once per (hospital, month).** `_compute_full_analysis` already computes
   `disabled_ids` at line 472 and again at 644 (fallback) and 472->`get_required_indicator_codes` at
   316 inside a try. The integration should pass the resolved bool to all three, and the
   denominator helper should receive the already-computed bool rather than re-resolving.

### 3.4 Failure policy

Current state: 5 raising sites, 2 swallowing sites (`dashboard`, `confidence`). A DB blip can
therefore produce a dashboard that recomputes completeness with the flag OFF while the stored score
was computed with it ON, and reports success.

**Recommendation — one policy, two presentations:**

* **Eligibility paths (analysis, smart, rules, clinical, preview): fail closed loudly.** If the
  configuration store cannot be read, raise `PolicyUnavailable`; the run fails and is visible. Never
  analyse with a guessed flag.
* **Presentation paths (dashboard, confidence, indicator tree): fail closed visibly.** Resolve with
  `strict=False`; if `read_error` is set, do not recompute - return the stored `QualityScore`
  values and add `"configuration_unavailable": true` to the response. Do not substitute `False`
  and recompute, because that silently changes the number on screen.
* **One implementation point:** `PolicySnapshot.read_error` already carries the distinction; the
  plan is to make every consumer branch on it instead of on its own `try/except`.

This is a behaviour change only on a database-failure path; it is listed as precondition P1 because
it changes error behaviour, not analysis output.

## 4. `smart_analytics` specification

### 4.1 Why a specification is needed

`_load_config` returns raw `AppConfig.value` for every `smart_analytics` row with the `smart_`
prefix stripped. There is no type coercion, no bounds check, no default table and no "invalid"
concept. Every consumer restates its own default inline, so the effective policy is the union of 15
read sites. The P0 defect: a value that is legal to store can abort the run
(`contamination=0`, `lof_neighbors=0`) or silently change a threshold.

### 4.2 The specification (proposal: `SMART_CONFIG_SPECS`, modelled on `severity.SettingSpec`)

| DB key | Short key | Plane | Default | Type | Valid range / values | Current coercion | Current invalid behaviour | Consumers | Analytical identity? | Editable? |
|---|---|---|---|---|---|---|---|---|---|---|
| `smart_enabled` | `smart.enabled` | smart gate | `1.0` | bool via `> 0.5` | 0..1 | `config.get(...,1.0) > 0.5` | any value >0.5 is ON; `"0"` (str) raises TypeError | `smart/__init__` -> 3 detectors | yes (suppresses stored smart output) | **yes** |
| `smart_contamination` | `smart.contamination` | smart value | `0.05` | float | `(0, 0.5]` | `float()` | out of range -> sklearn `ValueError`, **uncaught -> run fails** | `anomaly`, `explainability` | yes | yes |
| `smart_lof_neighbors` | `smart.lof_neighbors` | smart value | `5` | int | `2 .. n-1` | `int(min(v, n-1))` | `0`/negative -> `ValueError`, uncaught -> run fails; `1` -> sklearn warning | `anomaly` | yes | yes |
| `smart_dbscan_eps` | `smart.dbscan_eps` | smart value | `1.5` | float | `> 0` | `float()` | `<= 0` -> every point is noise (no crash) | `clustering` | yes | yes |

| `smart_xgboost_enabled` | `smart.xgboost_enabled` | smart gate | `1.0` | truthy | 0/1 | `config.get(..., True)` | `0` skips XGBoost only | `smart/__init__` | yes | yes |
| *(not seeded)* `smart_fdr_q` | `smart.fdr_q` | smart value | `0.05` | float | `(0, 1]` | `float()` | non-numeric -> `ValueError`, **uncaught -> whole smart run fails** | `correlations` | yes | **decide: seed it** |
| *(not seeded)* `smart_pattern_min_support` | `smart.pattern_min_support` | smart value | adaptive `min(0.25, max(0.12, 3/n))` then clamped to `[0.10, 0.45]` | float | `0 .. 1` after clamp | `float()` if non-empty | non-numeric -> `ValueError`, **contained** (`run_smart_analytics` catches around `detect_composite_patterns` and returns `[]`) | `patterns` | yes | **decide: seed it** |
| `smart_xgb_n_estimators` | — | **none** | `100.0` | — | — | — | **no consumer** | — | **no** | **no — remove or wire** |
| `smart_xgb_max_depth` | — | **none** | `4.0` | — | — | — | **no consumer** | — | **no** | **no — remove or wire** |

### 4.3 Behaviours that must not be "fixed" during integration

1. `smart_enabled` does not gate correlations or stratification.
2. XGBoost has its own flag and runs with smart analytics off.
3. Ensemble weights are applied raw and the result is min-max normalised, so only the **ratio**
   matters; a weight set summing to 1.0 is not special and normalising them would be a no-op that
   invites a future "fix" with real effects.
4. `pattern_min_support` keeps its adaptive default and its two-stage clamp `[0.10, 0.45]`; the
   snapshot must carry the *effective* value and its provenance, not just the stored value.
5. Invalid `contamination` / `lof_neighbors` keep failing (loudly after A3.3, not silently clamped):
   clamping would change which hospitals are flagged, which is an analytical change requiring
   separate approval.
6. `fdr_q` and `pattern_min_support` remain consumed with their current defaults until the seed
   decision (section 10, P3) is approved.

### 4.4 Where the smart plane lives

`smart.*` must **not** enter `values` under the `analysis` digest: a change to `contamination` would
then move the digest of a `QualityScore` it cannot affect. It gets its own scope digest (section 6).
It also must not be resolved before `_load_config` is replaced in the same change - otherwise two
differently-parsed sources coexist and the bug surface doubles.

## 6. Digest scopes

### 6.1 Recommendation: three scope digests, one snapshot

| Digest | Entries that participate | Attached to |
|---|---|---|
| `analysis_policy_digest` | P1 analysis values + P2 analysis gates + `identity_metadata` (`rules.hash/count/fields`, frozen constants, component versions) | `QualityScore` runs, alerts rows, diagnosis runs |
| `smart_policy_digest` | P1 smart values + P2 smart gates (+ same frozen constants/versions) | smart analytics cache entries, stored reports, XGBoost model metadata |
| `dashboard_policy_digest` | P3 (`anomaly_drift_months` only, for now) | attention-list responses, dashboard cache keys |

Why three and not one: the brief's own stop condition is that a digest must not present a
dashboard-only setting as analysis policy. A single digest that includes
`anomaly_drift_months` would move whenever an operator changes a display knob, and a single digest
that excludes it cannot identify the dashboard's own configuration. Three scopes cost one extra
function each and are derivable from the same entries.

Why not four (separate "flags" digest): the flag's effect is an *analysis* effect
(eligibility), so splitting it out would separate a setting from the output it changes.

### 6.2 Implementation shape (proposal)

```python
SCOPE_KEYS = {"analysis": (...), "smart": (...), "dashboard": ("dashboard.anomaly_drift_months",)}

def scope_digest(snapshot: PolicySnapshot, scope: str) -> str:
    payload = {"resolver": snapshot.resolver_version,
               "components": dict(snapshot.component_versions),
               "values": _normalise({k: snapshot.entries[k].value for k in SCOPE_KEYS[scope]}),
               "metadata": _normalise(snapshot.identity_metadata),
               "frozen": _normalise({k: e.value for k, e in snapshot.frozen_constants.items()})}
    return hashlib.sha256(json.dumps(payload, sort_keys=True,
                                     separators=(",", ":")).encode()).hexdigest()
```

`PolicySnapshot.digest` stays as-is (all entries) for backward compatibility with A3.1b; the scope
digests are additional views. No existing digest byte changes when the new keys are absent.

### 6.3 Association without a schema change

No column may be added in this phase. Options that need **no** migration:

1. **Structured log line at run start:** `policy_digest`, `resolver_version`, `invalid_keys`,
   `read_error`, hospital/month. Already half-present (`_compute_full_analysis` logs invalid keys).
2. **`GET /config/policy/digest`** returning `snapshot_provenance()` plus the three scope digests —
   a read-only endpoint; adding it is an API addition, not a response-contract change.
3. **Cache keys** for smart analytics and dashboard include the relevant scope digest, so a
   configuration change invalidates rather than reuses a stale cached result.
4. **Response metadata** on new endpoints only (never on existing response models).

Options that need a migration (deferred, separate approval):
`quality_scores.policy_digest` (additive nullable), `quality_alerts.policy_digest` (already stores a
fingerprint in `severity_policy.policy_fingerprint` form).

Honest limitation: with no stored digest, a historical `QualityScore` cannot be *proven* to have
been computed under a given policy after the fact. Logs give a time-correlated answer; only a
column gives a row-level one. A3.3 must not claim row-level provenance.

## 8. Failure policy (recommendation, not implemented)

| Path class | On unreadable config | On invalid individual value |
|---|---|---|
| Analysis run | raise `PolicyUnavailable`; run fails visibly | resolver records `invalid` + default; warning logged; **never** silently re-clamped |
| Alerts scan | abort with `configuration_error` (today's behaviour) | same |
| Smart analytics | raise; the API's existing error envelope reports it | current behaviour preserved per key (some fail loudly, patterns contained) |
| Dashboard / confidence / tree | `strict=False`; render stored values + `configuration_unavailable: true`; never recompute with a guessed flag | defaults with visible provenance |
| Preview | raise (a prediction built on a guessed policy is misleading) | same |

Removing the two silent `False` fallbacks is the only behavioural change recommended here; it
affects error paths only.

## 9. Migration order for A3.3 (no step may skip parity)

1. **Flags plane, no consumer change.** Add `auto_disable_null_indicators` and
   `dashboard.anomaly_drift_months` resolution + scope digests. Consumers still read the DB.
   Parity: snapshot value == legacy reader for every fixture state.
2. **Explicit parameter on the eligibility helpers.** Add required keyword-only
   `auto_disable_null`; update all 16 call sites to pass a locally resolved value that is still
   read from the DB at the boundary. Behaviour byte-identical; test asserts both paths agree.
3. **Boundary conversion.** Analysis, smart, preview, tree, dashboard and confidence resolve once at
   entry and pass the bool. `_is_auto_disable_null` remains only for endpoints not yet converted.
4. **Remove the silent fallbacks** (precondition P1).
5. **Bulk snapshot hoisting** (precondition P2).
6. **Smart plane**: replace `_load_config` with `SMART_CONFIG_SPECS`, seed/remove the two dead keys
   and decide `fdr_q` / `pattern_min_support` (precondition P3).
7. **Logging/endpoint association** for the three digests.

Steps 1-3 are strictly behaviour-preserving. Steps 4-6 change error paths and (for the dead seeds)
the settings UI, not analytical output.

## 10. Preconditions and verdict

| # | Precondition | Why it needs explicit approval |
|---|---|---|
| P1 | Unifying the failure policy (no silent `False`) | changes behaviour on DB-failure paths; not an analytical change, but observable |
| P2 | One snapshot per bulk batch | assumes a configuration change mid-batch must not split the batch; repository evidence supports it, but it is a semantic choice |
| P3 | Disposition of `smart_xgb_n_estimators` / `smart_xgb_max_depth`, and seeding `fdr_q` / `pattern_min_support` | removing or wiring a seeded key changes the System Control surface (data/UI decision, not an analysis change) |

No stop condition is triggered by the design itself:

* a snapshot boundary exists on every path (table 2.1);
* the one incompatible pair (`dashboard`/`confidence` swallowing vs. analysis raising) has a single
  recommended resolution (section 8) and does not require an analytical change;
* no migration or database write is required for steps 1-3;
* the uncommitted work is isolable (all A3.2b additions are new untracked files);
* `anomaly_drift_months` is kept out of the analysis digest, so no dashboard setting is presented as
  analysis policy.

**Verdict: READY FOR A3.3 DESIGN REVIEW**, with P1-P3 to be decided before steps 4-6.
