# A3.5 — P3.2 Confidence Policy: Implementation Design

Status: **design only; P3.2b final review complete; P3.3 ready for approval. No implementation performed.**
Date: 2026-11-03.
Companion audit: `qa-d16/A3.5-P3.1-CONFIDENCE-AUDIT-AND-DESIGN.md`.

Purpose: define the exact implementation plan for replacing the mutable
`SIGNAL_WEIGHTS` global and Confidence's private database reads with an
immutable, request-scoped `ConfidencePolicy` carried by the existing
`PolicySnapshot`.

The seven approved architectural decisions are treated as fixed:

1. one immutable `ConfidencePolicy` with five weights, three cutoffs and Z;
2. resolution through `PolicySnapshot`, with explicit propagation;
3. `GET /confidence/weights` is strictly read-only;
4. PUT validates the complete effective five-weight configuration;
5. formulas, defaults, thresholds, bands, Z settings and severity are preserved;
6. no historical `ConfidenceScore` rewrite or backfill;
7. no migration or uniqueness constraint in this phase.

**`app/engine/confidence_policy.py`** — dependency-free policy module:

* `CONFIDENCE_POLICY_VERSION = "1.0.0"`

## 2. Proposed `ConfidencePolicy` fields and defaults

```python
@dataclass(frozen=True)
class ConfidencePolicy:
    rule_compliance: float
    historical: float
    cross_hospital: float
    trend: float
    completeness: float
    high: float
    medium: float
    low: float
    zscore_threshold: float

    @classmethod
    def defaults(cls) -> "ConfidencePolicy": ...
    def weight_for(self, factor: str) -> float: ...
    def as_weight_mapping(self) -> dict[str, float]: ...
```

| Field | Default | Source | Semantics |
|---|---:|---|---|
| `rule_compliance` | 0.55 | weights row, else code | weighted signal |
| `historical` | 0.10 | same | weighted signal |
| `cross_hospital` | 0.10 | same | weighted signal |
| `trend` | 0.10 | same | weighted signal |
| `completeness` | 0.15 | same | weighted signal |
| `high` | 80.0 | `confidence_high` AppConfig, else code | `>=` → HIGH |
| `medium` | 50.0 | `confidence_medium` | `>=` → MEDIUM |
| `low` | 25.0 | `confidence_low` | `>=` → LOW, else CRITICAL |
| `zscore_threshold` | 2.5 | `thresholds.zscore_threshold`, raw | historical/cross `passed` and recommendations |

The dataclass stores scalars, so it has no mutable mapping field. `weight_for`
returns `getattr(self, factor, 0.0)`; the five signal factor names are the
approved set, and the fallback preserves the old `.get(..., 0)` behavior for an
unexpected signal.

The Z value is deliberately the **confidence** resolver entry, not
`severity.zscore_threshold` or `alerts.z_threshold`. It is unclamped and
unrounded; for a stored 99, the policy carries 99 while severity carries 5.

The policy has no mutable global, no DB handle, no session, and no provenance
fields. Provenance stays on `PolicySnapshot`/`PolicyEntry`, where the resolver
already records source, storage, validation and errors.

## 3. Complete configuration-resolution flow

### Analysis run (`pipeline.run_full_analysis` → `_compute_full_analysis`)

```
run_full_analysis(session, hospital_id, month, policy=None)
  -> load_policy_snapshot(session) if policy is None       (one snapshot)
       -> AppConfig rows
       -> SystemSetting rows
       -> rules_version metadata
       -> ConfidenceWeights rows ordered by id, limit 2   (new, one query)
       -> resolve_policy(..., confidence_weights=..., conflict=...)
            -> _resolve_flags / severity / trend / alerts / comparison / scoring
            -> _resolve_confidence(cutoffs, raw Z, five weights)
            -> canonical entries + errors + digest
  -> _compute_full_analysis(..., policy=policy)
       -> confidence_policy_from_snapshot(policy)           (same object)
       -> calculate_confidence(confidence_policy=..., auto_disable_null=...)
```

No consumer re-reads `confidence_weights`, `thresholds` or `SystemSetting` for
Confidence. `ConfidenceWeights` is read once per snapshot, not once per
indicator or per hospital.

### Confidence display API (`/confidence/{id}`, `/summary`, `/compare/all`)

```
load_display_policy(db)                (memoized once per session)
  -> resolve_policy(strict=False)
  -> confidence_policy_from_snapshot(policy)
  -> calculate_confidence(..., confidence_policy=...)
```

`/compare/all` resolves the display policy before its loop and passes the same
object to every hospital. A configuration change during the loop cannot alter
later hospitals.

### Settings endpoints

```
GET /confidence/weights
  -> load_policy_snapshot(db)           (strict; read-only)
  -> confidence_policy_from_snapshot
  -> five JSON numbers

PUT /confidence/weights
  -> load_policy_snapshot(db)           (current effective values)
  -> confidence_policy_from_snapshot
  -> validate_weight_update(payload, current_mapping)
  -> one row update/insert of all five values
  -> one commit
```

### Strictness and missing rows

* **Strict analysis path:** a store read failure raises `PolicyUnavailable`;
  analysis reports the configuration error as it does today. Never substitute
  defaults silently.
* **Display path:** `load_display_policy` marks entries `unavailable` and uses
  documented defaults, allowing the UI to render and label the outage. The live
  Confidence helper still calls `require_auto_disable_null()`, so an unavailable
  gate raises rather than producing a confident result.
* **Missing `confidence_weights` row:** not an error. Weights resolve from
  `DEFAULT_WEIGHTS`, source `default`; GET returns those defaults; PUT merges
  against them.
* **Missing cutoff/Z row:** existing resolver behavior is unchanged: documented
  default, source `default`.
* **Invalid stored value:** individually reported in `snapshot.errors`; no
  silent normalization. Non-finite weights fall back to the complete code
  default set (never NaN arithmetic); finite but negative/out-of-total values
  remain value-exact for parity but are flagged `out_of_policy`.
* **Duplicate rows:** select the **lowest `id`**, record a `confidence.weights`
  error with validation `conflict`, and mark the five entries validation
  `conflict`. No row is deleted or modified by a read. See §8 for the rationale
  and residual risk.

## 4. Snapshot and digest versioning strategy

### Entries

Five new keys, component `confidence`, storage `confidence_weights`:

```
confidence.weight.rule_compliance
confidence.weight.historical
confidence.weight.cross_hospital
confidence.weight.trend
confidence.weight.completeness
```

Existing keys stay:

```
confidence.high
confidence.medium
confidence.low
confidence.zscore_threshold
```

### Digest

`PolicySnapshot.digest = sha256(canonical_json)` already covers every `values`
entry, so the five weights become part of policy identity automatically. This is
intentional: weights change the score and selected level, and Z changes signal
pass/fail and recommendations even when the aggregate score is unchanged.

Consequences to approve and document:

* **every snapshot digest changes once**, including runs with default weights;
* `RESOLVER_VERSION` becomes `1.4.0`;
* `component_versions["confidence"]` becomes `1.0.0`;
* the golden-master fixture and any stored digest comparison must be
  re-baselined deliberately;
* no weight is added to `PROVENANCE_METADATA_KEYS` and no weight is excluded
  from `canonical_json()`.

The old digest cannot be preserved while adding an analytical input. A second
“confidence digest” outside the main identity digest would make the main digest
claim two runs are identical when their confidence results differ; that is not
recommended.

Canonical order is already guaranteed by `_normalise`/sorted JSON and by the
fixed weight-name tuple. The digest must be independent of mapping insertion
order; a test passes the same weights in reverse order and asserts equal digests.

No normalization occurs at read. If normalization is ever wanted, it must happen
at the PUT write boundary before storage; otherwise the snapshot would describe
different numbers than the engine uses.

## 6. GET / PUT API contract

### `GET /confidence/weights`

Authentication: existing router dependency `analysis.read`.

Success `200`:

```json
{
  "rule_compliance": 0.55,
  "historical": 0.10,
  "cross_hospital": 0.10,
  "trend": 0.10,
  "completeness": 0.15
}
```

* Missing row → documented defaults, 200.
* Stored row → selected effective values, 200.
* Duplicate rows → lowest `id`, 200 (error recorded server-side); no write.
* Configuration read failure → `500`, matching the current endpoint's failure
  behavior. Never return assumed defaults as if they were stored.
* The response shape does **not** gain fields. Existing Settings and any
  external reader keep working.
* No `updated_at` in GET, as today.

Guarantees: zero `INSERT`/`UPDATE`/`DELETE`, zero `commit`, zero `refresh`,
zero row creation, repeated calls identical, safe on a read-only replica.

### `PUT /confidence/weights`

Authentication: existing `settings.write` dependency (in addition to router
read).

Request: JSON object, a subset of the five keys. Unknown keys are rejected.
At least one known key is required. Missing keys are merged from the **current
effective policy**:

* stored row when present (lowest `id` if duplicates);
* documented code defaults when no row exists.

Validation of the **complete merged set**:

1. each value is a JSON number (not `bool`, not a string);
2. each value is finite (`Decimal.is_finite()` after exact decimal conversion);
3. each value is `>= 0`;
4. sum the `Decimal(str(value))` values and require
   `abs(total - Decimal("1.0")) < Decimal("0.01")` (strict; exact `0.99` and
   `1.01` are rejected);
5. no normalization or rounding is applied; the merged values are stored
   exactly.

Failure returns `400` with a specific message; no `add`, `setattr`, `commit` or
schema change occurs. Success returns `200` with the five stored values plus
`updated_at` (preserved existing shape).

Examples:

| Current | Request | Result |
|---|---|---|
| defaults | `{"rule_compliance": 0.50, "completeness": 0.20}` | 200; stored `.50/.10/.10/.10/.20` |
| `.2` each | `{"historical": 0.10, "cross_hospital": 0.30}` | 200; stored `.20/.10/.30/.20/.20` |
| defaults | `{"rule_compliance": 0.60}` | 400; merged total 1.05 |
| defaults | `.54/.10/.10/.10/.15` (exact total 0.99) | 400; boundary is excluded |
| defaults | `.56/.10/.10/.10/.15` (exact total 1.01) | 400; boundary is excluded |
| defaults | `{"rule_compliance": -0.05, "completeness": 0.60}` | 400; negative |
| any | `{"rule_compliance": NaN}` / `true` / `"0.5"` | 400; finite numeric rule |
| any | `{"not_a_weight": 0.1}` / `{}` / `null` | 400 |
| no row | all five valid values | 200; one full row created |

If no row exists, create `ConfidenceWeights(**merged)` and commit once. If a row
exists, update all five fields (not only supplied keys) and commit once. On a
commit failure, roll back and return `500`; no partial commit is left pending.

### Residual concurrency limitation

GET no longer creates rows, so the original read/write race is gone. Two
**simultaneous first PUTs** can still both see no row and each insert one because
the approved phase has no unique constraint. No migration is added here. The
resolver's lowest-id selection keeps subsequent reads deterministic, but the
duplicate remains a data-integrity issue for the separately approved uniqueness
work. Concurrent updates to an existing row are last-write-wins; no cross-process
lock is introduced.

## 7. Legacy rows and missing-row behavior

| State | GET | PUT | Analysis | Historical score |
|---|---|---|---|---|
| no `confidence_weights` row | defaults, no write | merge defaults; create only on valid update | defaults | unchanged |
| one valid row | stored values | merge stored values; update all five | stored values | unchanged |
| one finite row with negative/out-of-total values | stored values; server logs/records out-of-policy | partial update merged with stored; may fail until all five corrected | stored values exactly, flagged; no normalization | unchanged |
| one row with NULL/non-finite values | complete code defaults; invalid entries/errors | current policy defaults; valid full update creates/fixes all five | complete defaults, no NaN | unchanged |
| duplicate rows | lowest `id`; conflict error | updates lowest `id`; conflict remains; no deletion | lowest `id`; conflict error | unchanged |
| row deleted after snapshot | snapshot still holds its values | next request defaults | current request uses snapshot; next defaults | unchanged |
| old `ConfidenceScore` rows | stored payload only | not touched | not recalculated | **no exact provenance** |

No backfill, delete, dedupe, recalc, schema change or historical rewrite occurs.
The database is read exactly as before; only the runtime path changes.

Historical limitation remains: `ConfidenceScore` has no weights, cutoffs, Z,
digest or resolver version (`models.py:622-643`). The API and audit screen must
not imply otherwise. `calculation_steps` labels its weights as current policy;
`/{id}/stored` remains a stored-output view. Exact historical reproduction needs
a separately approved provenance change.

## 8. Test matrix and exact expected results

The primary fixture is the same one used in P3.1: one hospital `H`, month
`2026-04`, `values={"2":300}`, no rules, no history, one hospital in
`all_hospital_data`, no children, key code `["2"]`. Its four non-rule signals
are all neutral `0.7` (recorded as applicable, not missing), rule compliance is
`1.0`, completeness is `1.0`. The exact default result is therefore:

```
raw = 1.0*.55 + .7*.10 + .7*.10 + .7*.10 + 1.0*.15 = 0.91
confidence = 91.0, level HIGH
```

With five equal 0.2 weights:

```
raw = (1.0 + .7 + .7 + .7 + 1.0)*.2 = 0.82
confidence = 82.0, level HIGH
```

A missing indicator `"16"` with no value contributes only rule compliance:
`55.0` under defaults, `20.0` under equal 0.2 weights (existing
`test_confidence_math_is_unchanged_by_the_flag` pins 55.0).

### 12.1 Duplicate `ConfidenceWeights` rows

#### Current behavior and required handling

`ConfidenceWeights` has an indexed `id` but no unique/singleton constraint
(`models.py:645-656`). Current GET, PUT and `calculate_confidence` all use
`.first()` without `ORDER BY`, so the selected row is database-dependent. The
P3.3 resolver must make the three states explicit:

| State | Resolution | Write | Provenance / warning | Confidence behavior |
|---|---|---|---|---|
| **Zero rows** | Code defaults: `.55/.10/.10/.10/.15` | None; never insert on GET | source `default`, validation `fallback` | Valid; **91.0/HIGH** on the standard fixture; no stale global |
| **Exactly one row** | That row | None on GET | source `database`, validation `ok` | Stored values exactly |
| **Multiple rows** | **Lowest `id`**, deterministic | None on GET; no delete, merge or repair | source `database`, validation `conflict`; a `PolicyError` records all observed row ids | Valid; selected values exactly; conflict is visible in `snapshot.errors` and the log |

The loader query is:

```python
rows = (db.query(ConfidenceWeights)
          .order_by(ConfidenceWeights.id.asc())
          .limit(2)
          .all())
selected = rows[0] if rows else None
conflict = len(rows) > 1
```

For a conflict, record:

```python
PolicyError(
    key="confidence.weights",
    raw={"row_ids": [row.id for row in rows], "count": len(rows)},
    reason="multiple confidence_weights rows; using lowest id",
    fallback=selected_values,
)
```

Each of the five selected entries gets `validation="conflict"`; the values
remain `source="database"` and `fallback_applied=False`. `GET` keeps its
existing five-field JSON body; the conflict is server-side in
`snapshot.errors`/logs. No automatic repair is permitted.

#### Option comparison

| Option | Advantages | Compatibility implications | Verdict |
|---|---|---|---|
| **Reject duplicates with a configuration error** | No ambiguity; corruption is impossible to miss; no arbitrary policy | If raised by `load_policy_snapshot`, the whole analysis run aborts before core results, not just Confidence; GET/Settings and confidence API fail. There is no admin dedupe endpoint, no uniqueness migration, and no permitted automatic cleanup, so an existing duplicate would leave the feature unusable until a separate data operation. | **Not recommended for P3.3** |
| **Select lowest `id` deterministically** | Deterministic across SQLite/PostgreSQL; existing duplicate environments keep functioning; no data mutation; later migration can resolve the cause | A stale or unintended low-id row may be selected, and the conflict is not visible in the five-field response body. The defect remains until the separate uniqueness work. | **Recommended** |

The deterministic fallback is not a claim that duplicates are acceptable. It is
the only option in this phase that both surfaces the integrity defect and keeps
analysis available without deleting or rewriting rows. The durable fix is the
separate uniqueness/dedupe migration.

`PUT /weights` updates the lowest-id row (all five fields) when duplicates
exist; it does not create a third row, delete the others, or merge them. If two
simultaneous **first** PUTs both observe zero rows, both may still insert one row
each because there is no unique constraint; subsequent reads use the lowest id.
That concurrency residual is unchanged by this decision and is explicitly out
of scope.

### 12.2 Weight-sum tolerance

#### Existing UI and API facts

* The five Settings controls are range inputs with `min=0`, `max=1`,
  **`step=0.05`**, and displayed to two decimals (`settings.html:209-268`).
  With five such values, a UI-produced total is a multiple of `0.05`; in
  practice the accepted UI total is `1.00` (`.95` and `1.05` are outside the
  tolerance).
* `updateWeightDisplay()` and the pre-save check use
  `Math.abs(total - 1.0) < 0.01`; the current save path checks weights only
  **after** it has already PUT `/config/` and silently skips the weights PUT
  when the sum is outside that strict range (`rules-manager.js:65-79,
  3267-3287`).
* The current API sums only the fields present in the request, then uses
  `abs(total - 1.0) > 0.01` with binary floats (`api/confidence.py:225-249`).
  Exact `0.99` and `1.01` are not reliably accepted: `0.99 - 1.0` is
  `-0.010000000000000009`, so the boundary is representation/order-dependent.
  `math.fsum` can produce a different side of the boundary, so it must not be
  used to define the contract.

#### Final decision: strict decimal `< 0.01`

The complete effective five-weight set is validated with exact decimal
arithmetic:

```python
from decimal import Decimal

WEIGHT_SUM_TOLERANCE = Decimal("0.01")

def _decimal(value: float) -> Decimal:
    return Decimal(str(value))

total = sum((_decimal(v) for v in merged.values()), Decimal("0"))
if abs(total - Decimal("1.0")) >= WEIGHT_SUM_TOLERANCE:
    raise ValueError(
        f"Weights must sum to 1.0 within 0.01 (got {total})"
    )
```

Consequences, stated explicitly:

* **Exactly `0.99` is rejected** (distance exactly `0.01`; the comparison is
  strict).
* **Exactly `1.01` is rejected** for the same reason.
* `0.9999999999999999` is accepted because its exact decimal distance is below
  `0.01`; a value just inside the boundary is accepted. The boundary is a
  decimal contract, not a fuzzy “approximately 1%” allowance.
* **Values are stored unchanged.** Validation converts a copy to `Decimal` for
  comparison only; the stored floats are the merged floats supplied by the
  caller. There is no rounding, truncation or normalization.
* **Normalization is prohibited.** The server never divides by the total,
  redistributes the difference, or silently repairs the row. Invalid input is
  rejected before any `add`/`setattr`/`commit`.
* `bool`, strings, `NaN` and infinities are rejected before the sum. `Decimal`
  handles decimal boundary precision; `math.fsum` and ordinary float `sum()`
  are not used for validation.

Compatibility: this preserves the observed Settings behavior (the UI’s strict
`< 0.01` and `.05` step), codifies the current API’s practical rejection of the
exact boundaries, and rejects any external client that relied on the nominal
inclusive reading. There is no in-repo client that sends `0.99` or `1.01`.
The API remains more granular than the range control: an API client can submit
values between `.05` steps that still total within tolerance; the range control
may display such a stored value at its nearest step. That is a UI presentation
limitation, not server normalization, and changing the slider step is not part
of P3.3. The authoritative save path validates before any `/config/` write and
surfaces a 400 rather than claiming success.

### 12.3 Z-score separation

Confidence and severity currently read the **same raw AppConfig key**
(`thresholds.zscore_threshold`), but they apply different transformations and
serve different consumers. They are not a shared resolved scalar and must not be
combined.

| Plane | Snapshot entry | Source and transformation | Consumers |
|---|---|---|---|
| **Raw Confidence Z** | `confidence.zscore_threshold` | `AppConfig` key `thresholds.zscore_threshold`; default `2.5`; **no clamp, no rounding** (`config_resolver._resolve_confidence:706-723`; old `confidence.py:473`) | `ConfidencePolicy.zscore_threshold`; passed to `_signal_historical` and `_signal_cross_hospital`; drives `passed` and the displayed z/detail; `passed` can change recommendations. | **Severity Z** | `severity.zscore_threshold` | Same raw AppConfig key; default `2.5`; **clamped to `[1.0, 5.0]`, rounded to 2dp** (`_resolve_severity:403-427`; `severity.py:524-556`) | `AnalysisConfig.zscore_threshold` → pipeline `anomaly_config` and layered detection (`pipeline.py:522, 574, 717`); trend policy; Quality Alerts scan replaces its local `cfg["z_threshold"]` with this clamped value (`quality_alerts.py:1560-1562`); Explain's `_zscore_threshold`. Exact examples to test:

* Stored `99`: `ConfidencePolicy.zscore_threshold == 99.0` while

* Stored `0.5`: `ConfidencePolicy.zscore_threshold == 0.5` while severity and

### 12.4 Diagnostics presentation contract

#### Defect being corrected

`get_calculation_steps` reads a stored `ConfidenceScore` and currently returns
hard-coded default weights (`calculation_steps.py:105-115`). `audit.js:229-250`
renders those weights under “How confidence is calculated” and also hard-codes
the `80/50/25` levels. When weights or cutoffs are customized, the screen can
make a historical stored score look as if the current policy produced it.

#### Exact `confidence` object

When a stored score exists, `get_calculation_steps` returns this additive shape:

```json
{
  "overall": 91.0,
  "level": "HIGH",
  "result_scope": "stored",
  "recorded_at": "2026-11-03T10:00:00",
  "provenance_available": false,
  "provenance_note": "The weights, cutoffs, Z threshold and policy digest used for this stored score were not recorded.",
  "signal_weights": {
    "rule_compliance": 0.55,
    "historical": 0.10,
    "cross_hospital": 0.10,
    "trend": 0.10,
    "completeness": 0.15
  },
  "signal_weights_scope": "current_policy",
  "signal_weights_source": "database",
  "cutoffs": {"high": 80.0, "medium": 50.0, "low": 25.0},
  "cutoffs_scope": "current_policy",
  "zscore_threshold": 2.5,
  "zscore_threshold_scope": "current_policy",
  "current_policy_digest": "<snapshot digest>",
  "current_policy_version": "1.0.0",
  "resolver_version": "1.4.0",
  "current_policy_warnings": []

```

Field rules:

* `overall` and `level` are **stored** values; `result_scope` is always
  `"stored"`. `recorded_at` is `ConfidenceScore.created_at` when available.
* `provenance_available` is always `false` in P3.3. No weights, cutoffs, Z,
  digest or resolver version were written with historical scores, and no
  backfill occurs. The note is not optional.
* `signal_weights`, `cutoffs` and `zscore_threshold` are the **current**
  effective values and carry `*_scope: "current_policy"`.
* `signal_weights_source` is `database`, `default`, `invalid` or `unavailable`:
  * `database`: all five selected values came from the stored row;
  * `default`: no row, documented defaults;
  * `invalid`: at least one stored weight was non-finite; the complete fallback
    set is shown and labelled invalid;
  * `unavailable`: the policy store could not be read; all three current blocks
    are `null`, their scopes are `"unavailable"`, and no default numbers are
    presented as current configuration.
* `current_policy_digest` is the resolved snapshot digest when available; it is
  the **current** policy identity, not historical provenance. It is `null` when
  the policy is unavailable.
* `current_policy_warnings` contains stable codes such as
  `"duplicate_confidence_weights_rows"`; no free-form secret or DB error text.

If there is no stored `ConfidenceScore`, `calculation_steps.confidence` remains
`null`; no current-only block is invented. If the current policy is unavailable,
the stored result is still rendered because it came from the row, but every
current-policy value is absent rather than defaulted for display.

#### UI contract (`audit.js`)

* The overall block is labelled **“Stored confidence result”**, with
  `recorded_at` when present and the stored level badge.
* A persistent note says: **“Historical result: the policy that produced this
  score was not stored. Current policy is shown for reference only.”**
* The weights section is titled **“Current policy weights (reference only)”**,
  not “How confidence is calculated.” Every value is visibly marked

* The level/cutoff line is built from `cutoffs` when available and labelled
  `current_policy`; it must not hard-code `80/50/25`. If `cutoffs` is null, the

* If `signal_weights` is null, the UI shows **“Current policy unavailable”**; it

* No UI action recalculates a historical score. The warning is informational;

#### Historical boundary

This contract does not make old scores reproducible. It does not add columns,
write a provenance envelope into `indicators_data`, backfill, or recalculate.
Those remain separate, migration-bearing work. A future provenance feature may
set `provenance_available=true`; it must not retroactively label existing rows.
