## 2. Rules configuration — inventory and call graph

### 2.1 Storage and writers

| Item | Location |
|---|---|
| Persistence | `AppConfig`, category `rules`, 5 rows |
| Seeded defaults | `app/main.py:108-112` — `eq_tolerance 0.01`, `month_over_factor 2.0`, `month_under_factor 0.5`, `maternal_over_factor 4.0`, `neonatal_over_factor 4.0` |
| Writer | `PUT /config/` (`app/api/config_api.py:608+`) upserts a numeric `AppConfig` row; there is **no** dedicated rules control in `PUT /control/settings` |
| Read | `app/config_utils.get_config_dict(db, "rules")` (category read) |
| Rule *definitions* | the `rules` table (`Rule.expression_type`, `params`, `severity`, `enabled`) — content, not settings; edited by `/rules` endpoints |

The five settings are the only rule **policy scalars**. Rule definitions are
row content and are already hashed into the snapshot as `rules.hash` /
`rules.count` metadata (`config_resolver.rules_version`, lines 870-915), but the
rows themselves are read per run (`load_rules_from_db`, `quality/rules.py:520`).

### 2.2 Resolver

`_resolve_rules_config` (`config_resolver.py:728-760`) resolves `rules.<key>`
entries with defaults from the immutable `RULE_DEFAULTS`
(`quality/definitions.py:18`, a `MappingProxyType` captured at import) and
component `rules`. `RULE_DEFAULTS` **is** the authoritative fallback for the
resolver; `_RULES_CONFIG` is not read for defaults.

### 2.3 The mutable global

`_RULES_CONFIG` (`quality/definitions.py:3-9`) is a plain module dict, mutated
in place by `set_rules_config(config)` (`quality/rules.py:11-12`). There is **no
`get_rules_config`**; consumers index the dict directly:

| Consumer | Lines | Reads at |
|---|---|---|
| `_eq`, `_vs`-based equality checks | `rules.py:94, 110, 131, 151, 179` | rule evaluation time |
| R051–R055 closures (month over/under factors) | `rules.py:482-486` | rule evaluation time (closure reads the global) |
| `compute_covered_codes` | `rules.py:602` | scoring/coverage time |

Writers of the global:

* `pipeline.py:511-512` — `rules_config = get_config_dict(session, "rules"); set_rules_config(rules_config)` inside `_compute_full_analysis`, i.e. **per hospital-month**.
* `pipeline.py:1033` — `set_rules_config(get_config_dict(session, "rules"))` inside `revalidate_hospital_months`, i.e. per hospital.

Both happen **after** the run's `PolicySnapshot` was resolved (line 479 / 1020).

### 2.4 Findings

1. **Stored settings:** the five keys above.
2. **Independent defaults:** `RULE_DEFAULTS` (immutable), `_RULES_CONFIG` (mutable, initialised to the same values), and the rule definitions' own `factor` params for `month_over`/`month_under` DB rules. Three sources of "the default" exist; the resolver uses only the first.
3. **Authoritative fallback:** `RULE_DEFAULTS` for the resolver; the *engine* silently uses whatever `_RULES_CONFIG` currently holds, so an engine call that never ran `set_rules_config` sees import-time values regardless of the database.
4. **Global changes between requests:** yes, at `pipeline.py:511` and `1033`.
5. **One hospital affecting another:** within a single batch, the value is re-read per hospital; a concurrent write to `AppConfig.rules` between two hospitals changes the second hospital's rule outcomes while both claim the same run. Across requests, the last writer wins.
6. **Concurrent contamination:** definite. `set_rules_config` is an unsynchronised `dict.update`; rule functions read the global when they execute, not when the run resolves its snapshot. Run A with `eq_tolerance=0.01` and Run B with `10.0` can each observe the other's value for R002–R005-style equality rules, R051–R055 and coverage.
7. **Historical provenance:** none for rule settings. Persisted `ValidationResult` rows record the outcome and details, not the tolerance/factor used; the snapshot digest records the values but is not stored with validation rows. The `rules` table content hash is in snapshot metadata only.
8. **Snapshot plane unused:** `rules.*` entries are resolved but no consumer reads them (no `policy_view` adapter, no `snapshot.values["rules…"]` reference). The plane is currently dead weight — which is what makes the migration low-risk on the read side and high-value on the write side.

### 3.2 Resolver

### 3.3 Engine

`anomaly/trends.py`:

* `_TRENDS_CONFIG` (`16-29`) mutable module dict; `TREND_ENGINE_DEFAULTS` (`38`) immutable copy.
* `set_trends_config` (`48-67`) mutates it and counts calls (`_SET_TRENDS_CONFIG_CALLS`), warning at call 1 and every 100th.

* `analyze_historical_trends` (`204-330`) computes `settings`/`bands` from the resolved view, but its finding gates use `raw = dict(_TRENDS_CONFIG); raw.update(config)` (`219-221`) — so any gate missing from `config` comes from the **process global**.
* `detect_trend_anomalies` (`~333-420`) falls back to `_TRENDS_CONFIG["zscore_threshold"]` when `config` lacks the key.

| Smart/lag/regional | own settings (out of A3.5 scope) | — |

### 3.5 Findings

1. **Centrally resolved:** every `TREND_SETTING_SPECS` key, the four bands, the z threshold, and the five leftover engine gates (all present in the snapshot).
2. **Still read directly from the DB:** the five leftover gates are re-read through `get_config_dict(session,"trends")` in the pipeline and again in `explain`; `load_analysis_config` re-reads both stores for every API call.
3. **Resolver vs engine defaults:** identical for the five gates (`TREND_ENGINE_DEFAULTS` is captured from `_TRENDS_CONFIG`), identical for spec keys (shared `TREND_SETTING_SPECS`), identical for bands and z. The only divergence is `explain.py`'s `25.0`.
4. **Mutable at module level:** yes, `_TRENDS_CONFIG`, still written by the pipeline on every hospital-month.
5. **Leakage:** `_TRENDS_CONFIG` persists across requests. A request that passes a partial config (analysis API, file-ops, explain) inherits whatever the last pipeline run wrote for the missing gates. A request that passes nothing at all (tests/scripts) runs on whatever the process last configured.
6. **Same snapshot across one operation:** only partially. The pipeline's spec keys, bands and z come from the snapshot; the five gates come from a fresh DB read; the engine then overlays both on the global. Two of three sources agree only because they read the same rows moments apart.
7. **Different defaults/fallbacks:** `explain.py` 25 vs engine 20 for `trend_finding_deviation`; `detect_trend_anomalies`'s global z fallback; `_resolved_settings`'s global base.

### 3.6 The 25 vs 20 discrepancy — actual effect

`audit/explain.py:1782-1787` builds a display `thresholds` dict with
`trend_finding_deviation = float(tc.get("trend_finding_deviation", 25.0))`;
the engine default is `20.0` (`trends.py:27`, seeded at `main.py:178`).

* When the row exists and is readable, both read the same number: **no effect**.
* When the row is missing or unreadable, Explain states 25% while the engine used 20% (or the process-global value). Findings themselves come from `row.findings`, already computed by the engine, so the numbers and findings shown are unchanged — the displayed **threshold** is wrong.
* The same dict omits the other four finding gates from the snapshot, so Explain's displayed thresholds can disagree with the engine whenever `_TRENDS_CONFIG` differs from the DB (e.g. an operator changed settings after the last analysis).
* Not corrected in this phase.

## 4. Confidence configuration — inventory and call graph

### 4.1 Ownership split

| Value | Owner | Storage |
|---|---|---|
| 5 signal weights (`rule_compliance 0.55`, `historical 0.10`, `cross_hospital 0.10`, `trend 0.10`, `completeness 0.15`) | `ConfidenceWeights` table, one row | `confidence_weights` (`models.py:645-656`, no unique constraint) |
| Cutoffs (80/50/25) + z (2.5) | `thresholds` AppConfig | `app_config` |
| `SIGNAL_WEIGHTS` | code default | `confidence.py:41-47` |

Boundary: `/confidence/weights` `GET` (`api/confidence.py:204-220`) **creates** a
row with the five defaults if none exists (a GET that writes); `PUT`
(`222-246`) validates `sum ≈ 1.0` and writes the row.

### 4.2 Resolver

`_resolve_confidence` (`config_resolver.py:682-725`) resolves the three cutoffs
and `confidence.zscore_threshold` with component `confidence`. **It does not
resolve the five weights**, so `PolicySnapshot` has no confidence-weights
entry at all.

### 4.3 Consumers

`calculate_confidence` (`confidence.py:411-509`):

* `global SIGNAL_WEIGHTS` (`427`).
* If `session is not None`: reads `ConfidenceWeights.first()` (`431-437`) and **reassigns the global**; then reads `thresholds` again through `get_config_dict` (`442`) into `threshold_config`; both inside a bare `except Exception: pass`.
* If no row exists, the global keeps whatever a previous call left — the code default only until the first row is observed.
* Indictor score uses `SIGNAL_WEIGHTS.get(...)` (`479`); `_compute_level` (`349-362`) uses `threshold_config` with literal 80/50/25 defaults.

No other app module reads or mutates `SIGNAL_WEIGHTS` (docs/tests aside).
`api/confidence.py:208` independently restates the five defaults — a third copy.

### 4.4 Findings

1. **Managed by System Control:** cutoffs and z (AppConfig); weights via a separate screen/table.
2. **In `ConfidenceWeights`:** the five weights only.
3. **DB overriding code defaults:** yes, but by mutating a process global, not by resolving a value for the call.
4. **`calculate_confidence` mutating `SIGNAL_WEIGHTS`:** yes, line 434.
5. **Global across concurrent operations:** yes. Two runs with different weight rows interleave; each indicator's weighted sum reads the current global, so a batch can produce a mix of both weight sets.
6. **Same snapshot as the rest of the analysis:** no. The confidence step runs after the snapshot and re-reads its own two stores.
7. **Independent reconstruction:** `api/confidence.py:208` restates the defaults; no other consumer does.

**Classification:** the weights, cutoffs and z do **not** share one owner
(table vs AppConfig) and must not be flattened into one plane silently. A
`ConfidencePolicy` adapter may present them together, but each value keeps its
own storage and provenance.

## 7. Concurrency and isolation risks (source locations)

| # | Risk | Location | Effect |
|---|---|---|---|
| R1 | Rules global overwritten per hospital-month | `pipeline.py:511` | two concurrent runs see each other's tolerance/factors; equality rules, R051–R055 and coverage change |
| R2 | Revalidation writes the rules global | `pipeline.py:1033` | a revalidate request changes a simultaneous analysis request's rule outcomes |
| R3 | `/rules` preview/test never loads rules config | `api/rules.py:378, 544, 454, 578` | preview uses the last analysis's settings, not the stored ones |
| T1 | Trend global overwritten per hospital-month | `pipeline.py:526` | concurrent runs cross-contaminate finding gates, bands and z |
| T2 | Engine falls back to the global when config omits the five gates | `trends.py:219-221, ~400` | analysis API, file-ops and Explain depend on the last pipeline run |
| T3 | Pipeline mixes snapshot and DB reads for trends | `pipeline.py:520-526` | one run can use a snapshot value for bands and a fresh DB value for finding gates if a write lands between reads |
| C1 | `SIGNAL_WEIGHTS` mutated per call | `confidence.py:427-437` | concurrent runs compute weighted scores under each other's weights |
| C2 | Missing weights row leaves the previous global in place | `confidence.py:431-437` | a deleted/absent row silently reuses an earlier request's weights instead of the documented defaults |
| C3 | `GET /confidence/weights` inserts a row | `api/confidence.py:204-217` | a read mutates; two concurrent first reads can create two rows (no unique constraint) and `.first()` becomes arbitrary |
| E1 | Explain reads a second trend config after using another | `explain.py:1754-1786` | displayed thresholds can disagree with the values the engine used |
| S1 | Rules table content read per hospital, not snapshotted | `quality/rules.py:520`, `pipeline.py:556` | a rule edit mid-batch changes later hospitals; only a hash is recorded |

No concurrency safety may be claimed from snapshot immutability while these
globals remain: the snapshot is immutable, the consumers are not.

## 9. Concurrency and isolation test design (to be written later)

All tests use the `db_session` fixture's temporary SQLite database and
`threading.Barrier`/monkeypatched pauses — no sleeps as synchronisation, no
production data.

**Rules**
* `test_rules_two_threads_different_tolerance_do_not_leak`: thread A sets 0.01,
  thread B 10.0, barrier, both evaluate a value pair that passes only under
  10.0; assert A fails, B passes.
* `test_rules_month_factor_isolated`: same for R051's `month_over_factor`.
* `test_rules_preview_uses_stored_values`: with stored 10.0 and a global left at
  0.01, `/rules/impact` must report the 10.0 outcome (currently fails).

**Trends**
* `test_trends_two_threads_different_finding_gates`: A `deviation=5`, B `=50`;
  barrier after `_resolved_settings`; assert each finding set matches its own.
* `test_trends_partial_config_does_not_read_global`: call the engine with a
  config lacking the five gates after setting a different global; assert the
  result follows the documented default, not the global (currently fails).
* `test_trends_snapshot_gates_match_engine`: compare the snapshot's five gates
  against what the engine used for the same run.
* `test_explain_threshold_matches_engine`: assert the displayed
  `trend_finding_deviation` equals the value the engine applied.

**Confidence**
* `test_confidence_two_threads_different_weights`: two sessions with weight rows
  (0.9/0.025×4 vs 0.1/0.225×4), barrier inside `calculate_confidence`; assert
  each overall score matches its own weights.
* `test_confidence_absent_row_uses_defaults`: after a run with custom weights,
  delete the row and call again; assert the documented defaults are used, not
  the stale global (currently fails).
* `test_confidence_call_does_not_mutate_module_state`: assert
  `SIGNAL_WEIGHTS` is unchanged after a call.
* `test_weights_get_is_idempotent_under_concurrency`: two first reads must not
  create two rows.

**Snapshot reuse**
* Instrument `load_policy_snapshot` and assert exactly one call per batch
  (upload, rescan, reports), and zero inside any rule/trend/confidence helper.
* AST test: no analytical module imports `get_config_dict` or `_RULES_CONFIG` /
  `_TRENDS_CONFIG` / `SIGNAL_WEIGHTS` (the A3.2c inventory test grows this way).

## 10. Target architecture (design only)

```
System Control (AppConfig / SystemSetting / confidence_weights / rules table)
        │  single writer per setting, validation at write
        ▼
Central resolver (config_resolver)
        │  one snapshot per operation, typed entries + provenance + digest
        ▼
Immutable PolicySnapshot
        │  frozen sub-policies, no DB handle
        ▼
Explicit consumer parameters (RulesPolicy / TrendsPolicy / ConfidencePolicy)
```

Concretely:

* **`RulesPolicy`** (frozen, 5 fields) built from the snapshot's `rules.*`
  entries; passed as `run_all_rules(ctx, rules)` / `dispatch_rule(rule, ctx,
  rules)` / `compute_covered_codes(..., rules)`. The R051–R055 closures take the
  factor from the policy instead of the global. `set_rules_config` and the
  mutable read path are deleted after one release of zero-caller logging.
* **`TrendsPolicy`** (frozen) carrying every `TREND_SETTING_SPECS` value, the
  four bands, the five finding gates and the z threshold. `analyze_historical_trends`
  and `detect_trend_anomalies` take it and never merge `_TRENDS_CONFIG`.
  `AnalysisConfig.trend_engine_config()` is replaced (or extended) by a
  snapshot adapter that **includes** the five gates, so `analysis.py`,
  `file_ops.py` and `explain.py` stop falling back to the global.
* **`ConfidencePolicy`** (frozen): five weights, three cutoffs, z, each with its
  own `storage`/`source`. The resolver gains a weights read (a third store) and
  records `confidence_weights` as the storage; a missing row yields the
  documented defaults with `source="default"` instead of leaving a stale global.
  `calculate_confidence(..., confidence: ConfidencePolicy)` deletes
  `global SIGNAL_WEIGHTS`; `_compute_level` takes the cutoffs from the policy.
* **`PolicySnapshot`** stays the only carrier; `policy_view` grows a
  `confidence_policy_from_snapshot` and a `trends_policy_from_snapshot`; the
  pipeline stops calling `get_config_dict` for rules/trends/rates and stops
  mutating globals.
* **Display paths** keep their tri-state/unavailable rendering; they may read
  the snapshot's non-strict variant, but must not silently substitute values.

Typed immutable sub-configurations are justified here: three storage owners,
seven consumer modules, and today's globals. No further abstraction (no generic
policy bus) is warranted.

## 11. Phased implementation plan (each step small and reviewable)

**P0 — lockstep baseline (no behaviour change).** Add golden-master tests
capturing rules results, quality score, trend rows/findings, confidence
scores/levels, alert evidence, dashboard/diagnostics/explain JSON for a fixed
fixture DB. Add the AST "no hidden reads" test in report-only mode.

**P1 — Rules.** Add `RulesPolicy` + `rules_policy_from_snapshot`; thread it
through `ValidationContext` (or explicit parameters) and the rule closures;
delete both `set_rules_config` calls; fix `/rules` preview to use the stored
policy. Parity + concurrency tests R1–R3. Remove `_RULES_CONFIG` reads last.

**P2 — Trends.** Extend the trend adapter to include the five gates; pass
`TrendsPolicy` end-to-end from pipeline, analysis API, file-ops and Explain;
delete `get_config_dict(...,"trends"/"rates")` and `set_trends_config`. Decide
the 25-vs-20 question explicitly (correct Explain or pin it as documented
legacy) — do not fix it silently. Parity + tests T1–T3 + explain threshold.

**P3 — Confidence.** Add the weights read to the resolver and the
`confidence` plane; introduce `ConfidencePolicy`; delete the global mutation
and the per-call weights/thresholds read; decide `GET /weights` semantics and
the missing-row default; keep `PUT` validation. Parity + C1–C3.

**P4 — Removal and guardrails.** Delete `set_rules_config`,
`set_trends_config`, `_RULES_CONFIG`, `_TRENDS_CONFIG` reads, `_SET_TRENDS_CONFIG_CALLS`;
turn the inventory AST test into a hard gate; update the A3.2c inventory.

Each phase ends with `git diff` review, the parity suite, the concurrency suite
and the focused tests of every touched module; no phase starts before the

## 15. Risks and unresolved architectural decisions

1. **Confidence-weights ownership.** The weights live in their own table, not in
   `AppConfig`/`SystemSetting`. Putting them in `PolicySnapshot` means the
   resolver reads a third store; keeping them outside means confidence still
   resolves separately. Recommendation: include them, with `storage =
   "confidence_weights"`, but this needs approval.
2. **Rules table content.** Rule rows are content, not settings; only their hash
   is snapshotted. Whether a future phase should freeze the evaluated rows (so a
   mid-batch rule edit cannot change later hospitals) is undecided.
3. **Explain's 25% default.** Correcting it changes displayed explanations;
   preserving it keeps a known inconsistency. Needs an explicit choice.
4. **`GET /confidence/weights` writing.** Removing the insert changes the
   behaviour of a read endpoint; keeping it keeps the race and the duplicate-row
   risk.
5. **Removal of `set_*_config`.** External scripts/tests may still call them;
   the deprecation counters exist for trends but not rules. Removal needs a
   release of zero-caller evidence.
6. **Strictness.** Whether an unreadable `confidence_weights` row should fail an
   analysis (like the A3.3 gate) or fall back to documented defaults is a policy
   decision, not an implementation detail.
7. **Performance.** A snapshot that includes weights adds one query per
   operation — negligible, but the pipeline currently resolves per hospital in
   some paths; the migration should keep one snapshot per operation to avoid
   turning that into per-hospital overhead.
