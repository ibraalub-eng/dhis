The `trends.py` edit deserves justification: the five legacy trend gates exist only as literals
inside the mutable `_TRENDS_CONFIG` global, which a previous run can overwrite. Reading that

the resolver a stable source without restating the numbers, and leaves `_TRENDS_CONFIG` the same
mutable dict it has always been — its contents, the setter and the A2 shim are unchanged.

New non-configurable metadata: `rules.hash` (SHA-256 over every non-timestamp column of every rule
row, ordered by code), `rules.count`, `rules.fields`, `rules.updated_at`. It is carried in a new
`PolicySnapshot.metadata` mapping, is included in the canonical digest, and is deliberately **not**
in `values`, so it can never be edited as a setting.

Coverage decisions made from evidence, not assumption:

* `rules` defaults are imported from `quality.definitions._RULES_CONFIG` — the table the compiled
  rules actually read. Nothing is restated.
* `ml` coercions mirror `pipeline._build_ml_config`, including its plain truthiness for booleans
  (`bool(2) is True`) and `int()`/`float()` for the rest. A parity test compares the whole nested
  shape against that function, so a future edit there cannot leave the resolver behind.
* `alerts.auto_scan` reproduces the pipeline's exact parsing: the stored text form of
  `0 / 0.0 / false / False / off` is OFF, anything else is ON, absent is ON.
* the five trend gates take their defaults from `TREND_ENGINE_DEFAULTS`, and the resolver skips
  any key already owned by the setting specs, the bands or the Z-score plane, so nothing is
  resolved twice.

## 7. Remaining gaps before A3.2

1. **Snapshot metadata is DB-only by design.** The pure `resolve_policy()` accepts `metadata`, but
   only `load_policy_snapshot()` computes `rules.hash`; a caller using the pure path gets an empty
   metadata mapping. A3.2 must decide whether a configuration version can be built without a DB
   read (recommendation: no — versions are always created from a real snapshot).
2. **`auto_disable_null_indicators` is still outside the snapshot** yet changes eligibility. It
   needs a flag plane and a parity design before history can claim "complete configuration".
3. **`smart_analytics`, `clinical`, `risk`, `rates` remain uncovered** with the reasons in §3.
   D5's "all relevant categories" is satisfied under the relevance test, not literally.
4. **`policy_view` exposes only the A2 keys.** Nothing consumes `rules.*`, `ml.*`,
   `alerts.auto_scan` or the trend gates yet — that is correct for A3.1 but means the new coverage
   is proven, not yet *used*.
5. **Resolver version 1.1.0** now identifies this coverage. `component_versions()` reports `rules`
   and `ml` as `unversioned`; the rules table has a content hash in `metadata` instead.
6. **A1's "no restated defaults" rule needed one exception** for the `ml` coercions (the pipeline
   function is private and importing it into the resolver would invert the dependency). It is
   guarded by a parity test rather than by a comment.

## Erratum — A3.1b (policy resolver integrity remediation)

Four statements below are corrected here rather than rewritten in place, so the
review record shows what changed and why.

1. **Auto-disable readers were undercounted.** §Scope said `auto_disable_null_indicators`
   is read directly in five modules. It is read in **seven files through six readers**:
   `pipeline._is_auto_disable_null` (used at `pipeline.py:348`), the same helper via
   `smart/__init__.py:_disabled_maps`, and four independent `SystemSetting` queries in
   `confidence.py:452`, `dashboard.py:1522`, `tree_config.py:345` and
   `indicator_groups.py:456`, plus the writer in `config_api.py:65,243`.
2. **`smart_analytics` was misclassified.** It is not "a separate subsystem outside the
   snapshot scope"; nine of its keys decide calculations (contamination, ensemble
   weights, bands, DBSCAN) and two decide eligibility (`enabled`, `xgboost_enabled`).
   It is a **known, decision-affecting exclusion** pending its own increment — not an
   irrelevant category.
3. **`rules` defaults source.** The plane no longer reads the mutable
   `quality.definitions._RULES_CONFIG`. It reads `RULE_DEFAULTS`, an immutable
   `MappingProxyType` captured at import, so a runtime `set_rules_config()` cannot
   redefine "the default" or make a stored value report `source="default"`.
4. **`rules.hash` and `PolicySnapshot.digest` were conflated.** The hash never included
   timestamps; the digest did, through `metadata`. The digest is now explicitly a
   **policy-identity digest**: `rules.updated_at` stays on the snapshot for display but
   is excluded from `canonical_json()` via `PROVENANCE_METADATA_KEYS`. The hash field
   set also excludes the surrogate `id` and canonicalises `params` JSON. Contract
   details are in the `rules_version` docstring and the module header.

Also recorded, not corrected (out of A3.1b scope, analytical output would change):
`app/engine/audit/explain.py:1786` still defaults `trend_finding_deviation` to **25.0**
while the engine table and the seeded setting use **20.0**.
