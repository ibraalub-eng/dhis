## 4. Before/after configuration flow

**Before P2**

```
DB(app_config.trends + system_settings)
  ├─ pipeline: raw trends + raw rates + snapshot trend_engine_config()
  │            → merged dict → set_trends_config() → global
  │            (the five finding gates came from the raw DB read; the global
  │             was overwritten per hospital-month)
  ├─ analysis API: load_analysis_config → trend_engine_config()
  │            (five gates absent → engine fell back to the last writer's global)
  ├─ file_ops: same loader, same gap, once per batch
  └─ explain: same loader + a SECOND raw DB read for displayed thresholds
```

**After P2**

```
load_policy_snapshot(db)  ── one immutable snapshot per operation
        │
        └─ trends_policy_from_snapshot()
               = TrendSettings + bands + 5 gates + Z
               │
               ├─ analysis API  → analyze / detect (policy=)
               ├─ file_ops      → same policy object for every hospital
               └─ explain       → engine + displayed thresholds (one source)
```

`_TRENDS_CONFIG` remains only as the documented default table for the legacy
`config=` path; `set_trends_config` cannot change it.

## 5. TrendsPolicy fields and defaults

`app.engine.anomaly.trends.TrendsPolicy` (frozen; `bands` wrapped in
`MappingProxyType`):

| Field | Source | Default |
|---|---|---|
| `settings` (`TrendSettings`) | snapshot trend plane | window 12, min history 2, direction `any`, persistence 3, cumulative change 5.0, assessment enabled, severity policy `none` |
| `bands` | snapshot slope-band entries (monotonic floor applied by the resolver) | stable 2.0, low 5.0, moderate 15.0, high 30.0 |
| `finding_slope` | snapshot `trend_finding_slope` | 5.0 |
| `finding_deviation` | snapshot `trend_finding_deviation` | 20.0 |
| `finding_cv` | snapshot `trend_finding_cv` | 30.0 |

| `trend_r_squared` | snapshot `trend_r_squared` | 0.5 |

changed its meaning.

## 6. Explain 20% vs 25% decision

**Decision: 20% is the shared default; the 25% fallback is removed.**

Evidence:

1. `trends.py` engine default and the seeded `AppConfig` value are `20.0`
   (`TREND_ENGINE_DEFAULTS["trend_finding_deviation"]`, seed in `app/main.py`).
2. The resolver already resolves the gate with that default, and the A3.5 audit
   recorded the engine default as authoritative.
3. `explain.py`'s `25.0` was a display-only literal reached only when the
   `trends` row was missing or unreadable; findings shown were always
   `row.findings` from the engine, so no historical finding changes.

Boundary: the change affects only the **displayed threshold** in the Explain
payload when the stored row is absent/invalid. Stored values (e.g. 33.0) still
win (`test_explain_uses_a_stored_gate_over_the_default`); existing records are
neither rewritten nor re-explained retrospectively.

## 8. Concurrency evidence

`test_concurrent_evaluations_keep_their_own_policy` starts two threads on a
`threading.Barrier`; each calls `analyze_historical_trends` with its own
snapshot-derived policy (deviation gate 5% vs 1000%). The strict thread reports

is unchanged afterwards. `test_engine_ignores_a_poisoned_process_global`
additionally poisons `_TRENDS_CONFIG` directly and proves the supplied policy
still decides the finding.

## 13. Remaining limitations and NOT VERIFIED

* **No browser or live-server verification.** Constraint: the app server was
  not started. HTTP behaviour was exercised with FastAPI `TestClient` only.
* **P0 golden fixture is not a pre-P1 baseline** (§1.1); it remains a
  forward-looking parity lock.
* **Out-of-tree callers** of `set_trends_config` cannot be observed from this
  repository. The shim keeps them non-fatal and inert; P4 deletion should wait
  for a release with zero logged calls.
* **Invalid raw gate values** previously raised during comparison (no coercion
  in `analyze_historical_trends`). The snapshot path now coerces them and
  records `invalid`; this is a robustness change on a path that previously
  failed, not a change to any valid stored configuration. No test covers a
  malformed gate end-to-end through the HTTP API.
* **`rates` merge removal:** the merged keys were never read by trend
  computations (audit §3.4); removal is behaviour-neutral by inspection and by
  the passing trend suites, but there is no dedicated golden capture of the
  merged dict itself.
* **Static display/export paths** that only read stored trend rows were not
  modified and were not exhaustively re-tested beyond the suites listed.
