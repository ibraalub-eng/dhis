## 2. Implementation and call-site coverage

**Flag path.** `_compute_full_analysis` resolves the snapshot once (dead
re-resolution removed) and raises via `require_auto_disable_null()`.
`run_full_analysis` reuses that snapshot and computes
`auto_scan = policy.alerts_auto_scan` for
`_maybe_auto_scan_quality_alerts`, which now:

- has no `get_config_dict` call, no key-name read and no default parameter;
- is memoized per session+month exactly as before (one scan per month across a
  bulk upload);
- passes the same snapshot object to `quality_alerts.scan()`.

The pre-existing "config check failed, scan anyway" branch is gone by
construction: a configuration read failure aborts the run before the helper, so
there is no longer a path that scans under an unknown flag.

**Resolver behaviour preserved bit-for-bit.** `alerts.auto_scan` was already
resolved with `_AUTO_SCAN_OFF = {"0", "0.0", "false", "False", "off"}`; the old
consumer used the same list and an implicit ON default. Missing row → ON
(`source=default`); any other stored value → ON (`source=database`).

**Call-site coverage.** The alias-resolving AST walk over `app/` reports:


That is the corrected A3.3 figure (A3.3 counted 35 because its walk covered nine

**Display vs analysis.** `load_display_policy` now appears only in
`api/{dashboard,tree_config,indicator_groups,indicator_config,clinical,confidence,rules}.py`
— routes that render the tri-state `configuration_unavailable` — and in no
engine analytics module. `alerts.auto_scan` was deliberately **not** added to
`alerts_config_from_snapshot`: it is a run gate, not an alert-calculation input,
so alert outputs for identical configuration are unchanged.

**Displayed vs consumed.** `alerts_auto_scan` is an `AppConfig` row in category
`alerts`, exposed raw by `GET /config/{category}` and `GET /config/`, written by
`PUT /config/` (numeric coercion). The resolver reads that same row, and
`PolicySnapshot.alerts_auto_scan` is the boolean derived from it — the operator
sees the value that is consumed. No new control was added and no other parsing
site remains.

## 4. Snapshot consistency

One snapshot per operation, enforced end-to-end for this flag:

- single run: resolved at the entry point, `auto_scan` derived from it;
- bulk rescan/upload/reports/file-ops/tree-save loops: already resolve once
  before the loop and pass `policy=` (A3.3), so every analysis and its auto-scan
  share that object;
- the helper cannot fall back to a live read (no import, no `get_config_dict`,
  no default);
- `PolicySnapshot` remains `frozen=True`; two threads resolving different values
  keep their own result (tested).

## 6. Remaining gaps in central configuration

1. `_compute_full_analysis` still reads `rules`, `trends`, `rates`, `ml` and
   `quality` per hospital after snapshot resolution, and still applies rules and
   trends through `set_rules_config` / `set_trends_config`. `SIGNAL_WEIGHTS` in
   `confidence.py` is also process-global. **No concurrency isolation is claimed
   for these**; only the flag is isolated.
2. `run_full_analysis` converts `PolicyUnavailable` into the documented
   0-score fallback report (`issues: ["Analysis failed during report
   generation"]`); `recompute_hospital_months` logs and skips the month. This is
   the pre-existing failure policy, now documented in the A3.3 manifest §5a and
   unchanged here.
3. `load_display_policy` still serves display routes that call
   `require_auto_disable_null()` (dashboard list, rules preview, clinical,
   confidence, indicator config). They fail loudly on a degraded snapshot, but
   whether those calculations should resolve strictly is a separate decision.
4. `config_api.get_control_settings` still parses `auto_disable_null_indicators`
   with `row.value == "true"` instead of `parse_auto_disable_null`; identical
   result for the values that endpoint writes, but not the single parser.
5. `alerts.auto_scan` lives in the snapshot but not in
   `alerts_config_from_snapshot` by design; other alert settings (window,
   minimums, Z) remain snapshot-derived as before.
