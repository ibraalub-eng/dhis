## 5a. Failure behaviour and isolation — as-implemented record (A3.4)

- **Unavailable policy, analysis path.** `_compute_full_analysis` calls
  `require_auto_disable_null()`, which raises `PolicyUnavailable`; no default is
  substituted. `run_full_analysis` catches it in its generic handler and persists
  the documented 0-score fallback report with
  `"Analysis failed during report generation"` in `issues`, then returns it
  (pinned by `test_policy_snapshot_integration.py::test_analysis_reports_an_unreadable_configuration`).
  `recompute_hospital_months` logs and skips that month without incrementing
  `done`. This is the pre-existing failure policy, unchanged by A3.3/A3.4; a
  caller that must fail loudly has to inspect `issues` / the returned count, or
  the policy itself has to change in a separately approved phase.
- **Unavailable policy, quality alerts.** `quality_alerts.scan()` returns
  `{"configuration_error": True, "error": ...}`; it never falls back to
  hardcoded rules.
- **No concurrency-isolation claim.** The flag is a frozen per-run value and is
  thread-safe. `rules` and `trends` (`set_rules_config` / `set_trends_config`)
  and `confidence.SIGNAL_WEIGHTS` remain process-global mutable state written on
  every run; concurrent runs with different stored values can interleave. This
  was not tested or fixed in A3.3/A3.4 and must not be claimed as isolated.
