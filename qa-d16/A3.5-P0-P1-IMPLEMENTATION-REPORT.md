## 1. Golden-master baseline and results

Harness: `tests/a3_5_golden.py`
Baseline: `tests/fixtures/a3_5_golden_master.json`
Test: `tests/test_a3_5_golden_master.py`

Three reference cases over two hospitals (`General Hospital`,
`Central Medical`) and four months (`2032-10` … `2033-01`), all built from
in-test fixtures in a temporary SQLite database:

| Case | Stored `rules` rows |
|---|---|
| `default` | none — documented defaults only |
| `stored` | all five settings, non-default (`eq_tolerance 10.0`, `month_over 3.0`, `month_under 0.4`, `maternal_over 5.0`, `neonatal_over 3.5`) |
| `partial` | only `eq_tolerance 10.0`; the other four missing |

Captured per case and hospital: the effective resolved settings (`rules.*`,
trend deviation, z, confidence cutoffs), the persisted ValidationResult set
(code → status → details), Quality Score and its components/issues, the stored
Confidence Score, Diagnostics coverage codes, Dashboard completeness, the
TrendResult summary, and the alert row count. The auto-scan is disabled in
every case so the A3.4 run gate cannot introduce non-determinism.

Results: the fixture matches on repeated runs, and
`test_default_case_is_order_independent` proves that running the `stored` case
between two `default` cases does not change the second `default` output.

**Ordering caveat, stated plainly:** the harness and baseline were produced in
this implementation pass, after the P1 wiring, not as an independent
before-change artifact. They therefore freeze the current behaviour rather than
prove it changed nothing. The behaviour-preservation argument rests on three
other checks that do compare old semantics to new: (a) the new
`test_snapshot_policy_equals_the_legacy_category_read` asserts that
`RulesPolicy.from_mapping(get_config_dict(db, "rules"))` — exactly what the old
`set_rules_config` installed — equals the snapshot-derived policy for stored,
partial and empty cases; (b) the A3.1–A3.3 resolver parity suites still pass;
(c) the stored ValidationResult outcomes in the golden fixture are computed by
the real pipeline and would move if a formula, tolerance or default changed.

## 3. Rules consumers migrated, remaining callers

Migrated to an explicit `RulesPolicy`: `_ge/_gt/_ge_factor/_parent_le/_parent_lt/
_eq`, R051–R055 month factors, `run_all_rules`, `run_rules_from_db` →
`dispatch_rule`, `compute_covered_codes`, `get_covered_child_codes`,
`run_quality_analysis`, `pipeline._compute_full_analysis`,
`pipeline.revalidate_hospital_months`, `pipeline.compute_hospital_completeness`,
`outlier_eligibility._covered_codes`, `data_auditor`, `dashboard`
completeness, `explain` covered codes, `/rules/impact`, `/rules/test`,
`/confidence` recompute.

Remaining callers of `set_rules_config`: **none in `app/`.** An AST scan in
`test_pipeline_no_longer_writes_the_rules_global` walks every `app/**/*.py`
call node and fails on any call. `_RULES_CONFIG` is no longer read by the rule
engine (only exported for import compatibility); `RULE_DEFAULTS` remains the
immutable documented baseline used by the resolver.

Compatibility adapter: `set_rules_config(config)` is kept so an out-of-tree
import cannot crash, but it only increments a counter — it moves no state, so
it cannot contaminate a concurrent evaluation. It can be deleted in P4 after a
release with zero observed calls.

## 5. Concurrency test evidence

Two barrier tests in `tests/test_a3_5_rules_snapshot.py`:

* `test_two_concurrent_evaluations_keep_their_own_policy` — two snapshots
  (`eq_tolerance` 0.01 vs 10.0) enter `run_all_rules` simultaneously on the
  same data; the strict thread reports FAIL and the loose thread PASS.
* `test_two_concurrent_coverage_calls_keep_their_own_policy` — the same split
  for `compute_covered_codes`: `2.b` covered only under the loose policy.

Supporting assertions: the legacy table cannot change an evaluation even when
mutated directly; `set_rules_config` is inert; the pipeline contains neither the
setter nor `_RULES_CONFIG`; the AST zero-caller scan is empty.

Pre-existing exposure closed: `/rules/impact` and `/rules/test` no longer
depend on the global left by the last analysis, and the pipeline no longer
overwrites it per hospital-month or per revalidation batch.
