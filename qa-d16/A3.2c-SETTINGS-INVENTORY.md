## 1. Why this document exists

The governing requirement is that **System Control is the single authoritative
management source for every setting, and every consumer obtains its value through
one centralized resolution layer using one immutable snapshot per run**, with the
acceptance test:

> A setting is not considered centralized merely because it appears in the System
> Control interface or is included in a resolver that its consumers do not
> actually use.

That last clause is decisive here, because the codebase fails it in exactly that
way today: **66 seeded, editable settings have no reader at all**, while **8
consumed settings have no seed and no interface**. Those two facts are measured
below, not asserted.

Method: `APP_CONFIG_DEFAULTS` parsed with `ast` (no app import, no DB), every
Python source under `app/` and `scripts/` scanned for each key and for the access
helpers, and each consumer's read confirmed by its source. Where A3.2/A3.2b
already documented a figure, this document reuses it rather than re-deriving it.

| S4 | `indicator_definitions` table | formula + thresholds + `is_active` per indicator | — | Indicators screen | `indicator_service`, `rate_config` sync, clinical display |

`AppConfig.value` is a **Float** column: any non-numeric policy (enums, booleans
as text) cannot be stored there. That is why S2 exists, and why the trend enums
live in S2 while the trend bands live in S1 — a split with no principled rule
behind it, only history.

### 4.6 `smart_analytics` — 15 keys (analytical)

15 seeded; 13 consumed; 2 dead (`smart_xgb_n_estimators`, `smart_xgb_max_depth`).
Read through `smart._load_config`, which queries the category, strips the `smart_`
prefix, and returns untyped values with **no validation and no schema**; every
consumer then restates its own default (`config.get("enabled", 1.0)`,
`contamination 0.05`, `lof 5`, `eps 1.5`, `min_samples 3`, thresholds `0.3/0.6`,
weights `0.35/0.3/0.2/0.15`). So each value has **two default sources** (seed and
consumer fallback) and no type. Full spec: `A3.2b-INTEGRATION-DESIGN.md` §6.

## 6. Target architecture (as required, nothing implemented)

```
System Control (UI + API)  ──writes──▶  authoritative storage (S1/S2)
                                             │
                                   load_policy_snapshot(db)   ← the only read path
                                             │
                                 PolicySnapshot (immutable, scoped digests)
                                             │
        ┌────────────┬──────────────┬────────┴────────┬─────────────┐
     pipeline     dashboard     confidence        smart/ML      alerts/explain
```

Rules the migration must hold:

1. **One registry of metadata** (R5): a single table `key → storage, type, bounds,
   default, scope, owner screen, consumers, identity`. Existing spec objects
   (`SettingSpec`, `TREND_SETTING_SPECS`, `_ML_SPECS`, `RateSpec`) are imported by
   it; **no default is restated**, so seeding, validation, System Control display
   and resolution read the same constant.
2. **Values are passed, not re-read** (R3): the snapshot travels as an argument;
   the process-global setters are retired with their consumers.
3. **Failure is explicit** (R7): no `False`/default substitution on unreadable
   configuration (A3.2b §4 failure policy, precondition P1).
4. **Provenance is never implied** (R6): stored rows carry no configuration
   identity today; association is by digest log/endpoint, and that limitation is
   stated wherever historical data is shown.
5. **Dead settings are resolved, not inherited**: each dead key is either wired to
   a real consumer (with parity proof) or retired from the interface. Leaving them
   visible is what the acceptance criterion forbids.

## 8. Migration buckets (ordered, each independently reversible)

| Bucket | Content | Production risk | Gate |
|---|---|---|---|
| **M0** | this inventory + pins; registry skeleton fed by existing specs | none (docs/tests) | — |
| **M1** | flags plane: resolve `auto_disable_null_indicators`; required keyword arg on 3 helpers; failure policy | low, parity-tested | P1 |
| **M2** | smart plane: 15 keys typed/validated; remove per-consumer defaults | low, 34 differential cases | P1, P3 |
| **M3** | dashboard plane: `anomaly_drift_months` (+ dashboard digest); propagate `alerts_auto_scan`; unify month rule | low | — |
| **M4** | dead-seed disposition: 66 keys → wire or hide | **decision required** | user |
| **M5** | `ml` exposure: seed + validate 8 keys or mark ML unsupported | low | user |
| **M6** | clinical/risk adoption: move `_CLINICAL_META` into settings or delete the rows | **high** (would change classification if values differ) | separate approval |
| **M7** | historical provenance column | schema change | separate approval |

M6 is deliberately last and gated: adopting 45 seeded clinical thresholds would
make classification configuration-driven, which is a behaviour change unless the
seeded values are proven identical to the constants. The inventory shows they
agree today for cs/mmr/nmr etc., but proving all 15 families is a separate parity
job and is **not** authorized here.

## 12. Verdict

and measured. The system is **not** yet single-source-of-truth, and the two
reasons are precise: 66 settings are dead configuration and 8 are unmanaged, while
the resolver that would centralize the rest has no engine consumer yet.

Next action requires a decision, not code: choose the M4/M5/M6 dispositions, then
start M1 with the failure policy (P1) approved.
